# tools (second part)

The notes of `tools/make_kit.py` to `tools/zstd_compat.py`, in file-name order. Text a tool writes into a file it
generates (a `// Generated by ...` line, a manifest's `# path ...` header) is output, not a comment of the tool, and
stays in the tool as a string.

## `tools/make_kit.py`

Assembles the build kit: what a player needs to build the game on their own PC with `tools/make_game.py`
([README-BuildKit.md](../README-BuildKit.md)).

```
python tools/make_kit.py --xlate <dir with nx2navi_xlate.exe and .id> [--ffx amd_fidelityfx_vk.dll]
                         [--ffx4 FOLDER]
                         [--dlss nvngx_dlss.dll | --no-dlss] [--dlssg nx2navi_dlssg.dll [--streamline SDK]]
                         [--prompt-art FOLDER [FOLDER ...] | --no-prompt-art] [--out build/kit] [--zip]
```

The kit holds:

- the repository's `runtime/` with its shaders compiled (`tools/build_shaders.py` `build()` builds the missing and the
  stale SPIR-V headers here, so a player's PC needs no shader compiler; their sources go along), and `recomp/`;
- the build tools (`TOOLS`) and the shader translator built from `tools/xlate/`;
- NVIDIA's DLSS library with its notice (`tools/dlss_pin.py`: downloaded from NVIDIA's DLSS SDK repository and checked,
  or `--dlss`; not with `--no-dlss`). NGX loads it from beside the game (`runtime/vk/vk_dlaa.c`); `tools/make_game.py`
  copies it there;
- DLSS Frame Generation in `bin/dlssg/` with `--dlssg`: `nx2navi_dlssg.dll` from `tools/build_dlssg.py` beside NVIDIA
  Streamline's runtime (`tools/streamline_pin.py`: downloaded from NVIDIA's Streamline SDK release and checked, or
  `--streamline`). It is for `runtime/vk/vk_dlssg.c`; `tools/make_game.py` `place_dlssg()` copies it beside the game;
- AMD's FSR 3.1 library with `--ffx`, which FSR 3.1 loads from beside the game (`runtime/vk/vk_ffx.cpp`; its licence is
  `runtime/third_party/ffx_api/`), and its two FSR 4 libraries with `--ffx4`, loaded from beside the game too
  (`runtime/vk/vk_ffx4.cpp`; their licence is `runtime/third_party/ffx_sdk/`), with FSR 4's frame generation library
  when the folder has it (`runtime/vk/vk_fg4.cpp`);
- the button art, from which `tools/make_game.py` draws the button prompts in its prompts step;
- the pipeline list with `--pipeline-list`, as `tools/data/pipeline_list.bin`, where `tools/prepare_shaders.py` reads it
  (`BUNDLED_PIPELINES`);
- `README-BuildKit.md`.

It holds no game code, no game data and nothing generated from the game: `tools/check_content.py` `problems_for()` runs
over the folder before it is zipped, with large files allowed only for the translator and the DLLs.

The script stops before anything is downloaded when the `--xlate` folder does not hold a translator built from this
checkout's sources (`tools/build_xlate.py` `check_built()`), when the `--dlssg` DLL does not export every function
`runtime/dlssg/nx2_sl.h` declares (`tools/build_dlssg.py` `check()`: a DLL older than that header would leave features
out at run time without an error), or when a picture of the button art is missing (`tools/prompt_art.py`
`art_files()`).

The button art is the repository's `prompt-art` folder, or the folders `--prompt-art` names (folders that hold
`XGamepad`, `P5Gamepad` and `Keyboard_Mouse`, or those three folders themselves): the pictures `tools/pad_prompts.py`
reads go into the kit's `prompt-art` folder with its `SOURCE.md`, and `tools/make_game.py` draws the Xbox, PlayStation,
Steam Deck and keyboard and mouse prompts from them. With `--no-prompt-art` the kit builds the game with the game's own
prompts only.

Why `TOOLS` lists what it does beyond the tools `tools/make_game.py` runs directly: on Linux `tools/make_game.py`
imports `tools/build_game.py` `vma_include()` and `vulkan_include()` for the VMA header and for Vulkan headers newer than the system's
(which `tools/build_game.py` takes from `tools/vulkan_pin.py`); `tools/build_game.py` imports `tools/check_isa.py` and
`tools/build_shaders.py`, which reads the shaders of `tools/make_dlaa_mask.py` and `tools/make_mvobj_fs.py`; the lift
runs `tools/cheats.py` and `tools/exefs_patches.py` for the mods' code, and both import `tools/mod_files.py`; on a
Linux system without SDL3, `tools/make_game.py` `kit_sdl3()` fetches the pinned one with `tools/sdl3_pin.py` (an import
it guards, so that a kit without it asks for the system's package instead).

## `tools/make_launcher.py`

Builds a release of the launcher ([launcher.md](../launcher.md#releases)).

```
python tools/make_launcher.py --xlate build/xlate [--ffx amd_fidelityfx_vk.dll] [--dlss nvngx_dlss.dll | --no-dlss]
                              [--ffx4 FOLDER]
                              [--prompt-art FOLDER [FOLDER ...] | --no-prompt-art] [--out build/launcher-release]
                              [--pgo build/pgo/pgo-v111.profdata] [--feed owner/name]
                              [--notes notes.md] [--publish]
```

It needs Python 3.14 (`tarfile` and zstd for the MSYS2 packages), uv on PATH, network access on the first run, and
either Windows (msiexec, and the C compiler of MSYS2 it downloads itself) or Linux with clang, lld and llvm-windres
(it cross-compiles against the same MSYS2 packages) plus msitools. Downloads are cached in `toolchain/launcher-dl/` and
checked against the SHA-256 in `PINS`. `MAIN_ROOT` is the main checkout: `build/` and `toolchain/` are junctions in a
worktree. The `tcltk` pin is the Python installer's own Tcl/Tk and tkinter component, published beside it.
`DEFAULT_FEED` is this repository and its releases (`launcher/feed.py`, `DEFAULT`).

The release folder (`--out`) holds:

| File | What |
|---|---|
| `NX2Saria/` | the launcher folder exactly as `NX2Saria-Setup.exe` installs it |
| `NX2Saria/NX2Saria.exe` | `launcher/native/nx2saria.c` with the leaf sprig icon (`launcher/ui/art.py`) |
| `NX2Saria/python/` | python.org's embeddable Python 3.14.9, tkinter and Tcl/Tk 9.0 from its `tcltk.msi`, the packages of `tools/requirements-launcher.txt`, `runtime-id.txt` |
| `NX2Saria/app/current.txt`, `NX2Saria/app/<version>/` | see below |
| `NX2Saria-Setup-<version>.exe` | `launcher/native/setup.c` with the folder above appended as a zip: the one file players download |
| `NX2Saria-app-<version>.zip` | `app/<version>` alone: what the launcher downloads to update itself |
| `NX2Saria-runtime-<id>.zip` | `python/` alone: downloaded only when a release changes the Python |
| `NX2Saria-update.json` | the manifest the launcher reads (`launcher/feed.py`) |

`app/<version>/` holds `launcher/` (without `native/`), `runtime/`, `recomp/`, the tools `tools/make_game.py` uses and:

- `bin/nx2navi_xlate.exe` and `.id`; `amd_fidelityfx_vk.dll` with `--ffx`; AMD's two FSR 4 libraries with `--ffx4`;
- `bin/nvngx_dlss.dll` and its notice: NVIDIA DLSS at the version `tools/dlss_pin.py` pins, downloaded from NVIDIA's
  DLSS SDK repository and checked, or `--dlss`; not with `--no-dlss`;
- `bin/dlssg/` with `--dlssg`: `nx2navi_dlssg.dll`, Streamline's runtime DLLs and `nvngx_dlssg.dll` at the version
  `tools/streamline_pin.py` pins, downloaded from NVIDIA's Streamline SDK release and checked, or `--streamline`; their
  licences and a notice;
- `lib/libnx2navirt.a`: the runtime, prebuilt with the release's compiler;
- `data/pgo-v111.profdata` and `.json` with `--pgo`: the execution profile `tools/make_game.py` compiles the lifted code
  and the runtime with, the prebuilt runtime included, and its record (`tools/pgo.py` `merge()`);
- `prompt-art/`: the button art `tools/make_game.py` draws the Xbox, PlayStation, Steam Deck and keyboard and mouse
  prompts from (`tools/prompt_art.py` `art_files()`), with its `SOURCE.md`;
- `toolchain.lock.json` (the MSYS2 packages of today, pinned), `feed.json`, `VERSION` and the licence files.

The button art is the repository's `prompt-art` folder (CC0 pictures; its `SOURCE.md` says where they came from), or
the folders `--prompt-art` names: folders that hold `XGamepad`, `P5Gamepad` and `Keyboard_Mouse`, or those three
folders themselves. Only the pictures `tools/pad_prompts.py` reads are copied. With `--no-prompt-art` the release has no
`prompt-art` folder: the game keeps its own prompts and the Controls menu says the other prompts' files are missing.

`--pgo` names the execution profile of a play session ([building.md](../building.md), "Profile-guided build"). It is
derived from the game's code and stays out of the repository; its record must name this checkout's `recomp/`, or the
release stops (`tools/pgo.py` `fitting()`). Without it the release builds the game as before, the lifted code at `-O1`.
The profile is part of `NX2Saria-app-<version>.zip`, so an update brings it and the launcher's next build of the game
compiles with it.

`--publish` uploads the four files and the older update manifest's copy as GitHub release `v<version>` of the `--feed`
repository with the gh CLI (a draft first is wiser: `--draft`). `tools/check_content.py` runs over everything before it
is packed: the release holds no game data.

### `tcltk_files()`

The Tcl/Tk files of the pinned msi, unpacked into `WORK/tcltk` once. The stamp names the msi they came from and is
written last: an unpack from an older pin, or one stopped after `_tkinter.pyd` was written, is done again. On Windows
the unpack is an administrative image (`msiexec /a`): it copies the files and installs nothing.

### `build_python()`

The embeddable Python's `sys.path` is exactly the list written into `python314._pth`; `../pydeps` holds zbic
(`launcher/toolchain.py`).

### `check_xlate()`

A release carries the translator of its own sources. 0.10.0 and 0.10.1 shipped the 0.9.2 translator (identity
4d051299) after `tools/xlate/Program.cs` had raised the texture pool to 40960 slots, so their translations still
clamped every pool handle to slot 32767 and the ground went see-through after some area loads (issues #569 and #824).
A missing translator, or one whose `nx2navi_xlate.id` differs from this checkout's sources (`tools/build_xlate.py`
`check_built()`), stops the build; `main()` runs this before anything is resolved, downloaded or deleted. On Windows
the exe itself is asked too, as the `.id` says nothing of the exe beside it: a translator that declares the texture
pool with another length than its sources, or does not run, stops the build (`tools/xlate_smoke.py` `pool_check()`).

### `check_dlssg()`

A release carries an `nx2navi_dlssg.dll` that exports every function `runtime/dlssg/nx2_sl.h` declares. The runtime
takes a missing optional export (`nx2sl_reflex2`, `nx2sl_frames_max`) for an older DLL and leaves that feature out with
one log line, so a DLL built from older sources would ship without an error: with the DLL of 0.8.0, which lacks
`nx2sl_reflex2`, Reflex would never hold the frame limit. Such a DLL, or a missing one, stops the build
(`tools/build_dlssg.py` `check()`); `main()` runs this before anything is resolved, downloaded or deleted.

### `build_app()`

The runtime's own shaders are source in the repository and SPIR-V headers in a release: a player's PC compiles
`runtime/` (`tools/make_game.py`) and has no shader compiler, so the missing and the stale headers are built before the
copy. The translator files were checked first by `main()` (`check_xlate()`). What each optional file is for is as in
`tools/make_kit.py` above; `tools/make_game.py` copies the FSR and DLSS libraries beside the game. The execution
profile is placed (`tools/pgo.py` `place()`) before the prebuilt runtime is built with it; `tools/make_game.py`
`pgo_file()` is what compiles with it.

### `native_compiler()`

The compiler argv prefix and the windres argv prefix for x86_64 Windows: MSYS2's own clang on Windows, else the
host's clang against the same MSYS2 packages as a sysroot.

### `build_runtime_lib()`

`app/<version>/lib/libnx2navirt.a`: the runtime compiled once here with the release's MSYS2 clang, so players compile
only the few runtime files that include per-install headers (`tools/make_game.py --make-runtime-lib`). It needs
MSYS2's own `clang.exe`: native on Windows, through Wine with `--wine` elsewhere; without either, players compile
`runtime/` themselves.

The release's compiler is the one players build with (`toolchain.lock.json`): a profile it left out of the runtime
(`tools/make_game.py` `pgo_profile()` says why in its output) their builds would leave out too, so a release with a
profile whose `runtime-lib.json` does not record it stops.

### `build_native()`

MSYS2's GNU windres runs its preprocessor through `cmd.exe` and, left to find it, names the gcc beside it by full
path, which `cmd.exe` splits at a space once the `.rc`'s path holds one too. So gcc is given by bare name and found on
PATH (the toolchain's own `bin` first; no MSYS2 shell sets it), and the `.rc` by its name in the work folder, where
windres runs. llvm-windres (Linux) starts its preprocessor without a shell.

### `make_setup()`

`setup-stub.exe`, then the payload zip, then the 48-byte trailer `launcher/native/setup.c` reads.

### `write_update_manifests()`

Writes the manifest under both names, `NX2Saria-update.json` and `NX2navi-update.json`: launchers from before and
after the change of name find the same verified payloads.

### `main()`

`--publish` to `DEFAULT_FEED` is refused: this repository's own releases are built, attested and uploaded by GitHub
Actions only ([releases/README.md](../releases/README.md), "How a release is made"), so that players can check that no
file of them passed through anyone's PC. Before anything is downloaded, built or deleted it checks that the button art
is all there (`tools/prompt_art.py` `art_files()`), that the profile fits this checkout's `recomp/` (`tools/pgo.py`
`fitting()`), and that the translator and `nx2navi_dlssg.dll` are this checkout's (`check_xlate()`, `check_dlssg()`).

## `tools/make_mvobj_fs.py`

The SPIR-V of the per-object motion fragment shader as `runtime/mvobj_fs_spv.h`, which `runtime/vk/vk_exec_draw.c`
includes (the text of the header the tool writes still names that code's earlier file, `vk_mvobj.c`). It is
assembled here, word by word, because it must be patched at run time (the Location of its input follows the vertex
shader variant) and is small. `tools/build_shaders.py` writes the header from `HEADER` when the game is built; run on
its own (`python tools/make_mvobj_fs.py`), the script writes it too.

The shader, as GLSL:

```glsl
#version 450
layout(location = 0) in vec4 prev;            // last frame's clip position (patch 0015); Location patched
layout(set = 0, binding = 1, std140) uniform P { vec4 p; };   // render size xy, this frame's jitter zw (pixels)
layout(location = 0) out vec4 o;
void main() {
    vec2 win = gl_FragCoord.xy - p.zw;                         // this frame's window position, without the jitter
    vec2 pn = prev.xy / prev.w;
    vec2 pwin = vec2((pn.x * 0.5 + 0.5) * p.x, (0.5 - pn.y * 0.5) * p.y);
    o = prev.w > 1e-6 ? vec4(pwin - win, 0.0, 0.0) : vec4(0.0);
}
```

The vector is last frame's window position minus this frame's, in render pixels, as `runtime/shaders/dlaa_mv.comp`
writes it. Its descriptor set and binding are renumbered by `runtime/vk/vk_pipeline.c` like a translated shader's:
binding 1 is the fragment stage's slot 3, its parameters (`runtime/vk/vk_exec_draw.c`). The docstring said the
`.res.json` text of that code names it so; no such text is in the runtime now.

In the assembly, capability 1 is Shader, the memory model `0, 1` is Logical GLSL450, the entry point's model 4 is
Fragment and execution mode 7 is OriginUpperLeft. `Asm.loc_word` is the index of the patched Location literal in the
final words, which the header gives the runtime as `MVOBJ_FS_LOCATION_WORD`. The two runs of three multiply and add
instructions are x, `(nx * 0.5 + 0.5) * sx`, and y, `(0.5 - ny * 0.5) * sy`.

## `tools/make_romfs_patches.py`

Builds the 60 fps RomFS overlay for 1.1.0, 1.2.1 or 1.4.3 (`runtime/hle/romfs.c`, `NX2SARIA_ROMFS_PATCHES`). Its first
line is the notice of the code it holds from another project and stays ([THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md)).
The whole script runs at module level, the argument parser first.

`UI/LayoutArchive/Common.Product.<110 or 140>.Nin_NX_NVN.blarc.zs`: the weapon, shield and material quick menus capture
the game picture for their background when the panes `C_CaptureBG_00`, `C_CaptureClearBG_00` and `P_CaptureClearBG_00`
become visible at animation frame 1.0 (`anim/ShortCutBG_00_In.bflan`), AutoBuilder the same with `C_CaptureBG_00`
(`anim/AutoBuilder_00_In.bflan`): `MEMBERS`. UI animations advance 0.5 frames per game frame at 60 fps, so the capture
lands after the world stopped drawing and the background can be black. The visibility keys move to frame 0.0: the live
world is captured at once (the weapon, shield, material and ability wheels were checked at 60 fps and 30 fps).
`COMMON` is the version in the name of each game version's Common archive.

`--aspect <w>x<h>` (a game resolution of another shape than 16:9, such as 3440x1440 or 1280x800) also lays the UI out
for that shape (`tools/ultrawide_layout.py`): menus keep their 16:9 proportions in the middle, full-screen backgrounds
cover the screen and the HUD moves to the screen's corners (wider) or its top and bottom edges (narrower). The game
loads that overlay from `romfs-patches-<w>x<h>` when the game resolution is that size (`runtime/hle/romfs.c`
`overlay_init()`); the camera's side of it is the patch set `aspect` (`recomp/patches-v121.txt`,
`recomp/patches-v143.txt`). [wide-hud.md](../wide-hud.md) has the feature.

`--prompts xbox | xbox-label`: the same overlay with Xbox button icons in the game's prompts, for `prompts = xbox`
(`runtime/hle/romfs.c` `overlay_init()` loads `romfs-patches-xbox` or `romfs-patches-xbox-label` in place of
`romfs-patches`). Drawn from the game's own files on the player's machine, nothing added (`tools/button_icons.py`,
which needs fontTools):

- Both: L, R, ZL, ZR, Plus, Minus and the d-pad become LB, RB, LT, RT, Menu, View and a cross in the button font
  (`scft/External.bfotf`, the same font in each `Font/Font*.Nin_NX_NVN.bfarc.zs`), and L and ZL in the button guide's
  images (`Nt_KeyTexL_00` and `Nt_KeyTexZL_00` of `timg/__Combined.bntx` in the Common archive). The fonts grow, so the
  overlay also carries the resource size table (`System/Resource/ResourceSizeTable.Product.<n>...rsizetable.zs`, the
  newest `<n>` in the RomFS: `RESTBL`) with their entries raised by as much: an archive that grew needs as much more
  room in that table, or the game stops when it loads it.
- `xbox`, for `pad_layout = nintendo`. That layout plays an Xbox pad by position: the button that does Switch A is
  labelled B, so the face buttons' prompts are swapped to name the labels, A with B and X with Y (`by_position`):
  - The action prompt (`blyt/DoCommand_00.bflyt`) draws the letter images `Nt_KeyTexA/B/X/Y_00` of
    `timg/__Combined.bntx` in the Common archive: their image data is swapped (same format, size and tiling;
    `KEY_TEXTURES`). Around it, a diamond names the other face buttons with one-letter text panes (`T_B_00`, `T_X_00`,
    ...; `KEY_LETTERS`). The game fills them from the messages of the same name in `LayoutMsg/DoCommand_00.msbt` of
    each `Mals/<language>` archive, over the layout's own text: both have their letters swapped the same way. The
    diamond's shape (`Nt_KeyBtnSubBase*`) shows the button's position, which stays right.
  - Every other prompt: the glyphs U+E040 A, U+E041 B, U+E042 X, U+E043 Y of the button font trade places
    (`KEY_GLYPHS`).
- `xbox-label`, for `pad_layout = xbox` and `auto`. Those layouts put Switch A on the button labelled A (`auto` picks
  `xbox` for every pad not labelled the Nintendo way), so the face buttons keep their letters; the action prompt's
  diamond keeps the Switch positions (A on the right).

`--xbox-prompts` is the older name of `--prompts xbox`.

`--prompts pc`: keyboard and mouse prompts, for `prompts = pc` (`romfs-patches-pc`, or `romfs-patches-pc-<w>x<h>` with
`--aspect`): every button of the button font is drawn as the key or mouse button the keyboard defaults put on it
(`tools/button_icons.py` `pc_icons()`; `--binds <nx2saria.ini>` takes the first key of its `bind_` lines instead, or an
existing `nx2navi.ini`), and so are the button guide's images (A, B, X, Y, L, ZL and the stick's two). The one-letter
panes around the action prompt (`letter_panes`) name the keys with one character of the Normal font (E, an arrow for
Shift, a bar for Space, L and R for the mouse buttons).

Input: `build/extracted/<version>/romfs` (`romfs.bin` and `index.json`, verified by `tools/extract.py`). Output:
`build/<version>/romfs-patches/<path>` by default (`romfs-patches-<style>` with `--prompts`), and `<out>/manifest.tsv`
(path, size, SHA-256 of the overlay, SHA-256 of the original). It runs with `.venv-py314`
([building.md](../building.md)).

`MALS` is the message archive of each language, the newest version in the RomFS (`Mals/USen.Product.121.sarc.zs` on
1.2.1). `outputs` maps a RomFS path to its new contents before compression, `sizes` to the size of the original's
contents. Each distinct font is drawn once: 1.4.3's four font archives hold the same one.

### `sarc_nodes()`, `sarc_members()`

`sarc_nodes()`: name, node offset, absolute start and end of every SARC member, in SFAT order. `sarc_members()`: name
to absolute start and end.

### `flvi_keys()`

Pane name, absolute key offset and keys of every FLVI (visibility) step track in the BFLAN at `data[base:]`.

### `bntx_swap()`

Swaps the image data of each pair of textures in the BNTX at `data[base:]` (names without the `^` suffix). Both of a
pair must have the same header from flags to layout (format, size, tiling, mips) and the same image size, so the bytes
of one are a valid image of the other.

### `bflyt_letters()`

Swaps the text of the one-letter text panes `T_<letter>_<n>` (A, B, X or Y) in the BFLYT at `data[base:end]` by `swap`
(letter to letter) and returns the names of the panes changed. The length stays: one UTF-16 letter and its terminator.

### `msbt_letters()`

Swaps the one-letter messages labelled `T_<letter>_<n>` (A, B, X or Y) in the UTF-16 MSBT data (a bytearray) by `swap`
and returns the labels changed. The game sets a layout's text panes from the messages of the same name in
`Mals/<language>/LayoutMsg/<layout>.msbt`, over the text stored in the layout.

### `sarc_replace()`

The SARC data with the members named in `new` (name to bytes) replaced. The header, SFAT and SFNT stay; the members
are laid out again in their old order, each at an offset with at least the alignment its old one had.

## `tools/memgate.py`

A memory gate for parallel compiles, standard library only. The design, the measurements behind the numbers and the
build log's lines are in [build-memory.md](../build-memory.md); the notes here are those of the code.

The builds start each compile only when the memory free right now holds it. Each object's need is estimated from its
peak resident memory in earlier builds (`Estimates`), or from a size model before it has been built once. The gate
(`Gate` in-process, `wrap()` across processes for Ninja) admits a compile when the free memory, less what the running
compiles may still take and less a reserve kept for the rest of the machine, covers that need. The command line is the
rule command of each compile in a Ninja build:

```
python tools/memgate.py wrap --state DIR --name OBJ -- <compiler command...>
```

`hostmem` is imported a second time with the script's folder on `sys.path` when the first import fails: the script was
started with an isolated `sys.path`.

The constants:

- `MARGIN` (1.15) covers the variation of one object's peak between builds (different compiler flags, a slightly
  changed source). `FLOOR` (64 MiB) is a compile's smallest believable need: the compiler's own code and data.
- The model, for an object not built before, is a straight line in two sizes of its C source: all its bytes
  (`MODEL_PER_BYTE`, 50 MiB per million bytes of C, over `MODEL_BASE`), and the bytes of its largest function holding a
  jump-table branch (`switch_fn`, from the lift's manifest; `MODEL_PER_SWITCH_BYTE`, 150 MiB per million bytes), whose
  switch makes the optimiser's memory grow much faster than ordinary code does. Peaks measured with clang 20 at `-O1`:
  a 0.01 MB chunk 119 MiB (the compiler alone); ordinary 3 to 3.9 MB chunks 270 to 340 MiB; a chunk whose largest
  function is 2.5 MB without a switch 276 MiB; chunks whose largest function has a switch and is 1.8 MB 465 MiB, 2.8 MB
  663 MiB, 3.9 MB 922 MiB; `main_table.c`, 14.5 MB of tables, 582 MiB (the line over-estimates such data-only sources).
  The learned scale (`Estimates.scale()`) corrects the line per machine and compiler once enough objects have been
  recorded.
- `LEARN_TOLERANCE`: a recorded peak still applies while the source size is within 20 % of the recorded one, and its
  `switch_fn` too, unless both the recorded and the new one are below `SWITCH_SMALL`.
- `SCALE_MIN_SAMPLES`: recorded objects with a cost needed before the model's scale is learned. `SCALE_RANGE`: the
  learned scale is kept within it, so a few odd objects cannot run away with it.
- `RESERVE_MIN`, `RESERVE_SHARE`: the memory kept free for the rest of the machine is at least 1.5 GiB, or 10 % of the
  total RAM.
- `STDERR_TAIL`: characters of a compile's stderr that `run()` keeps. `PIPE_GRACE`: seconds `run()` still reads a
  compile's output after it ended (a descendant left running may hold the pipes open; the build does not wait for it).
  `HOLD_LOG_EVERY`: seconds between two "holding" lines. `POLL`: seconds between two looks at the free memory while a
  compile is held. `WAIT_NOTE`: seconds a wrapper waits before it says so on stderr. `LOCK_POLL`: seconds between two
  tries for the state folder's lock on Windows. `REPLACE_TRIES`: pauses between renames refused on Windows (a reader
  has the file open).

`Result.peak_bytes` is the peak memory of the process: resident (and on POSIX its waited-for descendants'), on Windows
the larger of the working set and the private commit; 0 when unknown. `Result.peak_commit` is the peak private commit
on Windows (already counted in `peak_bytes`), 0 elsewhere. `_Counters` is `PROCESS_MEMORY_COUNTERS_EX` and
`_ProcessEntry` is `PROCESSENTRY32W`; `_counters()` gives the memory counters of an open process handle or `None`, and
`_children_map()` the child pids of every parent pid now, from a process snapshot.

### `_pump()`

Reads a pipe to its end; writes each chunk to `sink` (a binary stream) when given; keeps the chunks when `keep` is a
list, trimmed to the last `STDERR_TAIL * 4` bytes as it goes, enough for `STDERR_TAIL` characters. A pipe closed under
it by `run()` ends the reading.

### `run()`

Runs a compile and measures it: its exit code, the last `STDERR_TAIL` characters of its stderr, its exact peak
resident memory and its wall time. stdout is read and dropped. `on_start(popen)` is called once the process runs (the
gate reads its resident memory by pid while it compiles). With `echo`, stdout and stderr are also passed through to
this process's own, as they arrive.

- The pipes are unbuffered objects: closing one while its reader thread waits in `read()` then needs no lock the
  reader holds.
- Where `os.wait4` exists the child is reaped here rather than through `Popen`, for its resource usage: `ru_maxrss` is
  the peak resident set of the child and of the descendants it waited for (bytes on macOS, KiB elsewhere). Setting
  `returncode` keeps `Popen` from reaping it again. A `ChildProcessError` means SIGCHLD is ignored, so the system
  reaped it already: `Popen.wait()` gives what it can, without a peak.
- On Windows the process object stays readable while `Popen` holds its handle, after the process has ended. Commit is
  what runs out on Windows (the page file backs it), so the peak is the larger of the two.

### `_proc_children()`, `rss_now()`, `_rss_reader()`

`_proc_children()`: the child pids of a Linux process, from the children lists of its threads. `rss_now()`: bytes
resident right now in a process and all its descendants; 0 when it cannot be read (a process that has ended, a system
without `/proc`). On Windows, `children` is a process snapshot (`_children_map()`) to reuse for several processes;
without it one is taken. `_rss_reader()` gives the reader for one admission decision: on Windows the default reader
then shares one process snapshot.

### `total_ram()`, `_cgroup_limit()`

`total_ram()`: bytes of memory the build may use: the physical memory, on Linux no more than the cgroup limit it runs
under; `None` when unknown. `_cgroup_limit()`: the tightest `memory.max` of this process's cgroup and the cgroups above
it (cgroup v2), or `None`. A build run under such a limit can use no more than it, so the reserve and the rule for
unknown free memory go by it.

### `_commit_left()`, `available()`

`_commit_left()`, Windows: bytes the system can still commit (`ullAvailPageFile` of `GlobalMemoryStatusEx`: RAM and
page file together, less what is committed), or `None`. A compile that cannot commit fails however much RAM is free.
`available()` is the free memory the gate goes by: `tools/hostmem.py` `available_ram()`, and on Windows no more than
the commit left, which runs out first on a PC with a small page file. `None` when neither can be read.

### `default_reserve()`

The memory kept free while compiles run: `RESERVE_MIN`, or `RESERVE_SHARE` of the total RAM when that is more.

### `start_time()`, `_alive()`

`start_time()`: when a process started, as a number that differs between two processes given the same pid one after
the other (Linux: clock ticks since boot, field 22 of `/proc/<pid>/stat`, read after the closing parenthesis of the
name, where the fields start at field 3; Windows: its creation time). `None` where unknown. `_alive()`: whether a
process with this pid exists; when `started` is given, also that it is the process that started then, not a later one
given the same pid.

### `model()`

The model's peak for a source of `src_bytes` whose largest function with a jump-table branch has `switch_fn` bytes,
before scale and margin.

### `Estimates`

Per-object peaks of earlier builds, kept as JSON: `{"version": 1, "objects": {name: {"peak": bytes, "seconds": float,
"src_bytes": int, "cost": int, "switch_fn": int}}}`. `cost` is the bytes of ordinary C the compile's time is worth (the
callers order compiles by it); `src_bytes` and `switch_fn` feed the size model; a lifted chunk has a cost above 0,
other sources 0. Safe to use from several threads. `_estimated` maps a name to how this build estimated it and the
bytes, `_ratios` to the recorded peak over this build's estimate.

### `Estimates.load()`, `Estimates.save()`

`load()`: the estimates stored at `path`; empty when the file is missing or unreadable. It never raises: an entry
whose number overflows `int()` (1e400 as a peak) is skipped, and so is deeply nested JSON from a damaged file
(`RecursionError`). `save()` writes the file atomically: a temporary file next to it, then a rename over it. A rename
Windows keeps refusing (another process has the file open) is retried a few times, then skipped: the estimates are
only a help, the next save writes them. True when written.

### `Estimates.record()`

Keeps a successful compile's peak (callers record only those). `keep_higher`: the compile ran while the free memory
was below the gate's reserve (`Lease.pressed`), where the system swaps or compresses pages and the measured peak can
come out low; a higher peak recorded before for the same object then stays.

### `Estimates.scale()`

How far real peaks are from the model: the median of peak over `model()` for the recorded lifted chunks (the objects
with a cost), kept within `SCALE_RANGE`; 1.0 until `SCALE_MIN_SAMPLES` of them are recorded.

### `Estimates.need()`

Bytes and how, for a compile. `learned`: the recorded peak, while the source size is close to the recorded one and so
is its `switch_fn` (each within `LEARN_TOLERANCE`, or both `switch_fn` below `SWITCH_SMALL`): after the lift groups its
functions anew, a chunk of the same name and size can hold other code. Otherwise `default` when the caller gives one
(sources the size model does not describe), else `model`. `cost` is not used here; it is the caller's order of
compiles and is kept with the record.

### `Estimates.stats()`

How this build's estimates were made, and how good they were: for each object both estimated and recorded, peak over
estimate (above 1: the compile took more than estimated).

### `owed()`, `admit()`

`owed()`: memory the running compiles may still take: for each, its need less what it already holds (all of its need
while its process is not known yet, rss `None`).

`admit()`: whether a compile needing `need` bytes may start now, with `running` compiles running whose need and rss
are in `running_needs_and_rss`. Fewer than `min_jobs` running: always (a build always progresses). `max_jobs` running:
never. Otherwise the estimated needs together stay under the ceiling, and the free memory (`avail`) less what the
running compiles still owe and less the reserve covers the need. When the free memory cannot be read (`avail` `None`),
the needs together with the reserve must fit in the machine's RAM (`total`); with that unknown too, only the
`min_jobs` compiles run.

### `Lease`

One admitted compile. `started()` gives the gate its process; it is released through the gate (or by leaving its
`with` block) once the compile has ended. `order` is 1 for the first compile the gate admitted, 2 for the next;
`held` the seconds the gate held it for memory; `sampled_peak` the highest resident memory the gate's sampler saw it
use; `lowest_avail` the least free memory the gate saw while it ran (at its admission and sampling). `Lease.pressed`:
whether the free memory fell below the gate's reserve while it ran; its measured peak may be low then.

### `Gate`

Admits compiles by the memory free now (`admit()`). Waiters are served in the order they asked; a waiter never passes
the one before it, so a large compile held for memory is not starved by small ones. When the free memory falls below
the reserve the gate only stops starting compiles; it never ends running ones. `total` is the RAM and decides only
when `avail()` is `None`; `_last_avail` is the free memory the last admission decision read. `_state()` gives need and
rss of each running compile, rss `None` for one whose process is not known yet.

### `Gate.acquire()`

Blocks until a compile of this need may start and returns the `Lease` to hand back to `release()`. `cancel` is called
while the compile waits; once it returns true the wait ends and `acquire()` returns `None` (nothing to release).

### `Gate._sample()`, `Gate.close()`

`_sample()`: every `poll` seconds while compiles run, the least free memory and the most resident memory of all the
running compiles together, for the summary. A reading that fails only loses one sample. `close()` stops the sampler.

### `gate_on()`, `settings()`

`gate_on()`: false when `--no-mem-gate` (`args`, which may be `None`) or the environment (`ENV_GATE` off, 0, no or
false) turns the gate off. `settings()`: the gate's settings from the options, else the environment, else the
defaults: `min_jobs`, `reserve` (bytes), `ceiling` (bytes or `None`), `enabled`.

### `prepare_state()`, `read_peaks()`

`prepare_state()` writes a state folder for `wrap()`: `config.json` from `settings()` and the job cap, `needs.json`
(object to bytes), and an empty ledger. Earlier `peaks.jsonl` lines are dropped. `read_peaks()`: the lines of
`peaks.jsonl`, skipping any that do not parse.

### `_Locked`

An exclusive lock on the state folder's `gate.lock`, held only while the ledger is read, decided on and written. On
Windows a refused try means another wrapper has it; it holds it only for a moment.

### `_replace()`, `_write_json()`

`_replace()`: `os.replace`, retried while Windows refuses it because another process has the file open; false when it
kept refusing. `_write_json()` writes a JSON file atomically; false when it could not be written.

### `_load_ledger()`

The ledger: `{'next': the next waiter's number, 'running': [entry], 'waiting': [entry]}`, each entry `{pid, start (the
wrapper's process start time), need, name, ticket}`, without the entries whose wrapper has ended. The second value
says whether any were dropped. A ledger that is a list is one of running entries only.

### `wrap()`

Waits for the gate, runs the compile, records its peak; returns the compile's exit code, a signal's number as a shell
reports it. Wrappers wait in the order they arrived: each takes a number in the ledger's waiting list, and only the
live waiter with the lowest number may be admitted, so a large compile held for memory is not passed by the small ones
Ninja keeps starting. A wrapper adds itself to the waiting list at its first look, and again when an earlier write was
lost; a lost write of its admission only leaves this compile uncounted.

### `_leave()`

Takes a wrapper out of the ledger. A failure is reported, never raised: the compile's exit code matters more, and the
next wrapper drops the entry anyway once this process has ended.

## `tools/menu_preview.cpp`

Draws the in-game settings menu and the performance overlay without the game, for looking at their design: the menu's
own row code (`runtime/ui/option_rows.cpp`), its shapes (`runtime/ui/menu_skin.cpp`), the overlay panel
(`runtime/ui/perf_panel.cpp`) and the text catalog (`runtime/ui/ui_text.c`), with the few runtime calls they make
answered here, laid out as `runtime/ui/menu.cpp` `layout_menu()` lays out the window. Dear ImGui's draw lists are
rasterised on the CPU into an RGBA image. Without an art folder the window has its plain border in place of the game's
ornamented frame and every box is plain shapes; with one (`tools/menu_preview.py --romfs`) the boxes use the game's
textures as in the game. The given font stands in for the game's either way.

`tools/menu_preview.py` builds and runs it:

```
menu_preview <font.ttf> <scene: menu | overlay | boot> <width> <height> <out.rgba> [art folder]
```

Settings come from `NX2SARIA_` environment variables over the few set here (`kSet`; `tools/menu_preview.py --lang` and
`--set` write them), and `MENU_PREVIEW_FOCUS` names the row that takes the cursor (`--focus`).

What the rows and the catalog ask of the runtime is answered with a few settings that have the menu's values and
defaults (`kMeta`):

- `strip()` gives the key without `NX2SARIA_` or the earlier prefix.
- `cfg_get()` reads the environment first, as the game does. `cfg_default()` has no device profile here: it is the
  row's own default.
- `cfg_pending()` is 0: nothing changed since the start, so no "after restart" notes. `cfg_supported()` is 1: every
  row is shown.
- The menu's draft (`cfg_state()`, `cfg_hold()`, `cfg_revert()`): nothing is applied or saved here.
- The quality presets: this PC gets medium (`cfg_preset_recommended()`), which sets nothing here, so
  `cfg_preset_differs()` is 0.

The game's art comes from files `tools/menu_preview.py` decoded: `NN.art`, a width and a height (32-bit) and the RGBA
pixels of the `MenuArt` NN, with the smaller levels the game uploads (`art_load()`). Texture ids in the draw lists: 1
is the font atlas, 2 and up the art (`menu_art()`).

### `backdrop()`

A dim field and sky, as the game shows behind the menu; then the menu's own dimming (`runtime/ui/menu.cpp`
`layout_menu()`).

### `scene_menu()`

The frame is drawn as `runtime/ui/menu.cpp` `layout_menu()` draws it. The first row takes the cursor as the menu
opens; a row named by `MENU_PREVIEW_FOCUS` takes it a frame later, as a key does in the game, once ImGui has given the
new window its first item. The rows are the Screen tab's first rows as `runtime/ui/menu.cpp` `tab_screen()` shows them
(the GPU row with a long name), the Quality preset row as `row_preset()` of that file shows a tier with keys set by
hand (custom), the Scene resolution row as its `row_scene_res()` shows the game's own share, and the Dynamic
resolution rows as its `row_dyn_res()` shows them without an upscaler.

### `scene_overlay()`

The numbers are those of the screenshot the overlay was redesigned from.

### `scene_boot()`

The boot screen's box over the black the window shows then (`runtime/ui/menu.cpp` `menu_boot_frame()`), half way
through the pipelines.

### `edge()`

Twice the signed area of (e0, e1, p), computed with the edge's ends in one fixed order, so the two triangles that
share an edge get exactly opposite values for a pixel and none is shaded twice or left out along it.

### `sample()`, `sample_art()`

`sample()`: the atlas at (u, v), bilinear, clamped to its edges; 0..1. `sample_art()`: the art at (u, v) at level of
detail `lod`, trilinear between its levels, as the game's sampler reads it.

### `raster()`

The rasteriser: every triangle of the draw lists, its colour times the font atlas (or the art), blended over the
image, whose pixels are straight RGBA, 0..1. It follows the top-left rule: a pixel centre on an edge two triangles
share is shaded by one of them only (edge k is the one opposite vertex k, run in the triangle's own winding). The
level of detail of an art texture is the texels per screen pixel along the steeper axis. The atlas is sampled
filtered, as the GPU samples the atlas's baked lines.

### `main()`

The scale is as `runtime/ui/menu.cpp` `menu_scale()` gives it at 100 % display scale. A few frames are drawn: sizes
settle and the first row takes the cursor.

## `tools/mod_files.py`

The player's mods folder as the game reads it (`runtime/patches/mods.c`): where each mod keeps its parts, and the
files of the mods that change the game's code. Standard library only: the launcher imports it from the kit's tools
folder.

One folder per mod (a symbolic link or junction to a folder counts). A part (`romfs`, `romfslite`, `exefs`, `cheats`)
is the first of `<mod>/<part>`, `<mod>/atmosphere/contents/<title>/<part>`, `<mod>/contents/<title>/<part>` and
`<mod>/<title>/<part>` that is a folder (`PLACES`; `runtime/patches/mods.c` `find_root()`). `TITLE` is the game's title
id: a mod's Atmosphere folders are named after it.

The files that change the game's code are a mod's Atmosphere cheat file for main's build (`<cheats>/<build id>.txt`,
the name in any case) and the ExeFS patch files (`.ips`, `.pchtxt`) of its `exefs` part and of
`<mod>/atmosphere/exefs_patches/<name>/`. The lifted game cannot be patched while it runs, so the build turns them into
patch sets (`tools/cheats.py`, `tools/exefs_patches.py`) and the runtime switches those on with their mod; a file the
build did not see waits for the next one. `tools/make_game.py` builds them in and records what it built
(`build-cache/mod-code.json`, `code_record()`); the launcher compares that record with the folder (`launcher/mods.py`)
to rebuild the game before it starts when a mod brought new ones.

### `mod_folders()`, `part()`

`mod_folders()`: the mod folders of the mods folder, by name (as the setup's tools list them: Python's order of the
names). `part()`: the folder of a mod's part, the first of its places that is a folder, or `None`.

### `cheat_files()`, `patch_files()`, `main_build_id()`

`cheat_files()`: mod folder name and cheat file for the folders of `mods`, by name: `<cheats>/<bid>.txt`, the name in
any case. `bid` is the first 8 bytes of main's build id in hex, as cheat files name themselves (`tools/cheats.py`
`build_id()`). `patch_files()`: mod folder name, path in the mod and file: the `.ips` and `.pchtxt` files of the
`exefs` part and of `atmosphere/exefs_patches/<name>/`. `main_build_id()`: the first 8 bytes of main's build id in
upper-case hex (the cheat files' name), `''` when main cannot be read.

### `code_files()`, `code_record()`

`code_files()`: mod folder name, path in the mod and file for every file of the mods folder that changes the game's
code: the cheat files for `bid`, then the ExeFS patch files. `code_record()`: `{"<mod>/<path in the mod>": sha256 of
its bytes}` of `code_files()`: what a build that lifts them in takes. A file that cannot be read is left out (the tools
would fail on it too, and the next build tries again).

## `tools/nup.py`

Reader for the `.nup` game container (little endian, nothing encrypted). Standard library plus zstandard. Each thread
reads through its own handle (`Nup._handle()`): seeks on one shared handle race.

```
0x00  superblock, 0x80 bytes: "NUP\x01", u16 0x80, u16 1, u64 toc offset, u64 toc size, sha256(toc),
      u64 blob offset, u64 file size, u32 package count, u32 0, 16-byte unique id, 32 zero bytes
TOC:  u32 "TOC\x01", u32 packages, u64 dirs, u64 files, u64 name pool offset (from the TOC), u64 pool length, u64 0
      packages, 0x40 each: u64 title id, u32 root dir, u32 exefs dir, u32 romfs dir, u32 version, u8 kind
                           (0 base, 1 update, 2 dlc), u8 flags, u16, u32, u64 meta offset, u32 meta length, 20 bytes
      dirs,     0x18 each: u32 name offset, u32 name length, u32 first child, u32 child count, u64
      files,    0x50 each: u32 name offset, u32 name length, u64 size, u64 data offset (absolute), u64 stored size,
                           sha256 of the file's bytes, u8 codec (0 stored, 1 one zstd frame), padding
      children: u32 each, a directory below the dir count, else dir count + file index
      names:    the pool
```

`Nup.__init__()` reads no more of the table of contents than the file holds, whatever the header says. The SHA-256
only says the table is what the file's writer wrote: counts and offsets that do not fit it end in a `NupError`, which
the callers report, not in `struct.error` or `IndexError`.

### `Nup.tree()`

Path relative to the directory and file index, for every file below it. A directory met twice (one listed as its own
child or ancestor) is a `NupError`, where it went round for good.

### `Nup.chunks()`

The file's bytes in pieces, checked against its SHA-256 at the end (`NupError` when they differ).

## `tools/pack_shader_cache.py`

Folds the loose files of a shader cache into `<cache>/shader-cache.pack` and deletes them.

```
python tools\pack_shader_cache.py <install folder>\shader-cache [--keep]
```

The translator writes four files per shader into the cache (`runtime/gfx/gfx_shader.c`): `<key>.spv`,
`<key>.res.json`, `<name>.use` and `in/<input id>.in`, about 117,000 files after an install, which are slow to copy,
back up, scan and sync. `nx2saria.exe` reads the pack first and the loose files after it, and keeps writing new
translations as loose files, so this tool can run again at any time the game is closed: it merges the existing pack
with the loose files (a loose file wins over a packed one of the same name) and writes the pack anew. The installer
runs it after preparing the shaders. `--keep` leaves the loose files in place. Close the game first: a running
`nx2saria.exe` has read the old pack's index.

Layout, little-endian (`runtime/gfx/gfx_shader.c`, its cache pack part): `b'TKSPACK1'`, u32 count, u32 0, then count
entries of 48 bytes sorted by (kind, name): name (the 32 bytes the file name's 64 hex digits spell), u32 kind (1
`.spv`, 2 `.res.json`, 3 `.use`, 4 `in/*.in`), u32 size, u64 offset; then the data.

`USE_SIZE` (20) is what `runtime/gfx/gfx_shader.c` `use_store()` writes: magic, version, three masks.

Loose files are read on `READERS` threads, at most `WINDOW` ahead of the one being written. On Windows the time goes
into opening each file (about 3 ms the first time, against 0.04 ms once the system has seen it), which threads
overlap: read one at a time, the 175,000 files of a launcher's cache took minutes.

### `loose_files()`, `read_pack()`

`loose_files()`: `{(kind, name): path}` of the cache's loose files; `*.in` only in `in/`. `read_pack()`:
`{(kind, name): (offset, size)}` of an existing pack; `{}` when there is none or it fails a check.

### `pack()`

With no loose file there is nothing to fold in: every file of the cache is already in the pack, so writing it again
would copy the same bytes over the same entries (1.37 GiB on the bench, 2.6 s, and a file system that then has the old
pack's blocks to release as well). The installer runs this after every prepare, so it returns at once.

The header and index are written once the offsets are known: zeros hold their place first. For each key the data is a
valid loose file, else the packed copy, else nothing. The `in` folder is removed afterwards only when empty.

```

`--art` is a folder of button art with the file names of `STYLES` (`tools/prompt_art.py`) and `KEY_ART`: the `Source`
folder of a button prompt art pack, which holds `XGamepad/Default`, `XGamepad/Light`, `P5Gamepad/Default`,
`P5Gamepad/Light`, `Keyboard_Mouse/Dark` and `Keyboard_Mouse/White` (128x128 PNGs: a dark button or key with a white
label, or a light one with a dark or coloured label), or a release's `prompt-art` folder, which holds the same files
(`tools/make_game.py` runs this tool on it): by default the repository's `prompt-art` folder (`tools/prompt_art.py`,
`REPO_ART`; CC0 pictures whose `SOURCE.md` says where they came from). The art is read where it lies.

`--game` is the folder of the port's exe and `romfs-index.bin`. The RomFS is read from its `romfs` folder
(`index.json` and `romfs.bin`, as the setup writes them); `--romfs` names another, which may also be a folder of
extracted files. Each pad style and layout becomes the overlay folder `<game>/romfs-patches-<style>` (layout
`position`) or `<game>/romfs-patches-<style>-label` (layout `label`), and the keyboard and mouse
`<game>/romfs-patches-pc`, each with a `manifest.tsv`: `runtime/hle/romfs.c` `overlay_init()` loads it in place of the
game's files when `nx2saria.ini` (or an older `nx2navi.ini`) has `prompts = xbox`, `playstation`, `steamdeck` or `pc`
(`runtime/input/input_map.c` `input_prompts_folder()`). Without `--style` or `--layout`, every style or layout. The
Steam Deck style has no art of its own: its buttons are named as an Xbox pad's face buttons and a PlayStation pad's
shoulders and stick clicks, so it is drawn from those two pads' pictures (`STYLES`). `--out` writes a single style and
layout elsewhere.

The two pad layouts follow `pad_layout` (`runtime/input/input_map.c`). `position`, for `pad_layout = nintendo`: a pad
is played by position, so Switch A is the right face button, labelled B on an Xbox pad and circle on a PlayStation
pad; the prompts for A show that button (A as B or circle, B as A or cross, X as Y or triangle, Y as X or square).
`label`, for `pad_layout = xbox`, `playstation` and `auto`: Switch A is the bottom face button, so A shows A or cross,
B shows B or circle, X shows X or square and Y shows Y or triangle. `FACE` is the face button that does each Switch
face button, by its place on the pad.

`pc` shows the first key each button has (`PC_KEYS`, the defaults, with the `bind_` lines of `--binds` over them; by
default `<game>/nx2saria.ini`, else an existing `<game>/nx2navi.ini`), the mouse buttons as a mouse, and for the right
stick the mouse moving. A key bound later shows after the tool runs again. The keyboard follows no pad layout: one
folder, `romfs-patches-pc`.

What changes, the rest of each file staying as it is:

- `Font2/Scalable/External.Nin_Ounce_NVN2.bfotf.zs`, the button font every prompt in text uses (dialogue, the button
  guides, the controls screen): the glyphs of the buttons (U+E040 A, B, X, Y, L, R, ZL, ZR, the d-pad, Plus, Minus,
  and the sticks and d-pad with their directions) become outlines traced from the art (`trace()`), at the size of the
  game's own face buttons; Power, Home, the console and the arrows stay. A `.bfotf` is a CFF OpenType font behind an
  8-byte header and an XOR (`tools/button_icons.py` `bfotf_decode()`); fontTools writes it again.
- `UI/Layout2Archive/Common.Product.100.Nin_Ounce_NVN2.bntx.zs`, the shared interface textures:
  `KeyTexFontA/B/X/Y_00`, the letter of the action prompt (`DoCommand_00`; 64x64 BC4 masks the layout tints), and
  `OcarinaButtonA/B/X/Y/L/R_00`, the ocarina's note buttons (`PaOcarinaSingleNote_00`; 93x93 ASTC 4x4 sRGB, a white
  button with a dark letter). They are painted again in place, in their own format, size and block-linear layout, so
  the archive keeps its size. `MASKS` and `NOTES` name them by Switch button.
- The resource size table (`System/Resource/ResourceSizeTable.Product.<n>...rsizetable.zs`): the font grows, and the
  game sizes the buffer it loads a file into from the table, so the font's entry is raised by as much
  (`tools/button_icons.py` `grow_restbl()`).

It needs fontTools, Pillow and zstandard (`tools/requirements-py314.txt`; the launcher's Python has them,
`tools/requirements-launcher.txt`). The two imports after the `sys.path` line carry `# noqa: E402` with what is taken
from each module (`bfotf_decode`, `bfotf_encode`, `redraw_font`, `grow_restbl`; the art and the folders), which stays.

The tables:

- `GLYPHS`: the Switch button each code point of the button font shows (the stick and d-pad glyphs name their
  directions). U+E06A is the d-pad with three directions lit; the art has no such picture, so it shows the whole d-pad.
- `PC_KEYS`, for `prompts = pc`: every button shows the first key its bindings give it. The defaults are
  `DEFAULT_KEYS` of `runtime/input/input_map.c`; `--binds` takes the `bind_` lines of a settings file over them. The
  right stick is the camera, which the mouse turns, so its prompts show the mouse moving (its arrow keys, a second
  source, do not show).
- `KEY_ART`: the art's name of each key (settings-file key names, `key_names` of `runtime/input/input_map.c`); letters,
  digits and F keys are their own. The art spells Ctrl as Crtl.
- `KEY_LABELS`: what a blank key shows for a key the art has no picture of (`label_art()`); any other shows its name.
- `PIECE`: how much of a packed file `unpack()` gives the decompressor at a time.
- `LIT_AREA`, `LIT_RING`: pixels of the art.
- `NOTE_BOXES`: where the game's own note buttons are opaque in their 93x93 textures (1.1.1), which the new ones fill:
  the face buttons a disc, L and R a wider shape. Measured once with the runtime's ASTC decoder
  (`tools/ui_textures.py`), so this tool needs none.

### `pad_pictures()`, `pc_keys()`, `key_picture()`, `pc_pictures()`

`pad_pictures()`: glyph and note pictures for a pad style, Switch button to picture, the face buttons through `FACE`.

`pc_keys()`: `PC_KEYS` with the first key of each `bind_<button>` line of a settings file over it. A line without a
key entry, or with `key:default` first, keeps the default (the prompt then shows a key the line took away).

`key_picture()`: the art of a key or mouse button in `shade` (`Dark`: a dark key with a white label; `White`: the
other way round), or a blank key with its name drawn on it when the art has none. The art names its dark 4 key
`T_3_Key_Dark-1`.

`pc_pictures()`: glyph and note pictures for the keyboard and mouse, by the key each button has. A d-pad or a stick
with several directions shows their keys in a grid, as they sit on the keyboard.

### `Romfs`

The RomFS: `index.json` and `romfs.bin` (each file's offset and size), or a folder of extracted files.
`Romfs.load()` gives the contents and the dictionary (or `None`) of a RomFS file, a `.zs` file decompressed with the
dictionary its frame names.

### `unpack()`

The contents of a zstd frame, with the dictionary it was packed with; bytes after the frame are left out.

The file goes to the decompressor in pieces of `PIECE` bytes and the pieces' outputs are joined once. Given the whole
file in one call, the library returns one bytes object that it grows by copying as the output comes: made-up data of
the size of the interface texture archive, 69 MB packed and 244 MB unpacked, took 21 s that way on a fast PC against
0.3 s in pieces. Players' builds waited 44 to 52 s before this tool's first folder, most of its minute.

### `sarc_members()`, `compress()`

`sarc_members()`: name to absolute start and end of every member of a SARC archive. `compress()`: a zstd frame of
`contents` with the dictionary the original used, so the game reads it the same way.

### `load_art()`, `grid_art()`, `label_art()`, `options_art()`

The art is a button as coverage, traced into outlines. `load_art()`: a picture as RGBA: a file under `art`, or one
drawn from several (`OPTIONS`, `('grid', cells)`, `('label', key, shade)`). `grid_art()`: keys side by side; cells are
(picture, column, row), row 0 on top, each centred in a cell as large as the largest key, with a small gap between
cells. `label_art()`: a key the art has no picture of, as its blank key with the key's name written on it.
`options_art()`: PlayStation's Options button as the art draws its Create button's neighbour on the pad: the dark pill
of the share picture with three white bars, drawn four times larger and scaled down for smooth edges.

### `ink()`

Coverage 0..1 per pixel (rows of floats) of a button drawn as a dark body with white symbols, for one-colour glyphs:
the body counts, and so does white outside it (a stick's direction arrows, which touch the transparent background);
white inside it (letters, symbols) is a hole. `lit`: a d-pad with its pressed directions in white. The art draws them
as a white arm in a hairline outline (Xbox) or as a white arm the others' colour reversed (PlayStation); at text size
the one vanishes and the other looks like the rest, so each white part of `LIT_AREA` pixels or more becomes a hollow
arm, a `LIT_RING`-pixel band along its edge.

### `symbol()`

Coverage of the white letter or symbol inside a dark button (the action prompt's letter), as an L image: the white
inside the body, the body's own grey left out.

### `_parts()`

Alpha and luminance (0..1) per pixel, whether each pixel is white outside the body or its soft edge, and the white
parts (lists of (x, y)). The background is the transparent pixels reachable from the edge. Each white part is outside
the body when a quarter of its edge touches the background: a stick's arrows touch it all round; a lit d-pad direction
inside a thin dark outline touches it only where the outline thins at a rounded corner, and stays a hole. The soft
edge of an outside part (antialiased pixels next to it) counts with it.

### `trace()`

Closed outlines (lists of (x, y) in pixels, y down) where `field` crosses `level`, by marching squares with the
crossings placed linearly along the cell edges. Each outline has the covered side on its left once y points up (as in
a font): outer outlines run counter-clockwise and holes clockwise, as a CFF font wants them.

- `v()` puts one pixel of zero around the field, so every outline closes; `cross()` returns its point back in field
  coordinates.
- `starts` maps an edge to the start point, end edge and end point of the segment leaving the cell through it. A
  cell's corners are taken clockwise with y down.
- `hits` are the crossings met going round the cell clockwise: edge key, point, and whether it enters the covered
  part. Each segment joins the crossing entering a covered part to the one leaving it, so that going round the cell
  clockwise (y down) the covered part lies between them.
- Four crossings are a saddle: the middle decides whether the covered corners join. The crossings are put in the order
  enter, leave, enter, leave first.

### `simplify()`, `outlines_of()`

`simplify()`: a closed outline with the points that stray less than `tolerance` from a straight line dropped
(Douglas-Peucker on the two halves between the first point and the one farthest from it). `outlines_of()`: the traced,
simplified outlines of a dark-style button picture, specks dropped (`lit`: as `ink()`).

### `draw_font()`

The button font with the glyphs of `GLYPHS` drawn from `glyph` (Switch button to picture). Every picture is scaled as
A's picture is to the game's A (both fill their square the same way; the game's A is a round button), centred in its
advance and placed at the height of the art's own square, so the arrows of a stick reach out as they do in the art. A
grid of keys is made no taller than the game's A and centred on it. A wider picture widens its glyph; `side` is the
room the game's A has on either side. `lit_dpad`: the d-pad directions are lit pad pictures (`ink()` with `lit`).

### `bntx_textures()`, `level_tiles()`, `block_linear()`

BNTX textures are block-linear in the Switch 2 GOB layout (`runtime/gfx/tex_deswizzle.c`, `nvn_bl_offset`).
`bntx_textures()`: name to format, width, height, block height (log2 GOBs), level offset and level size of every
one-level 2D texture of a BNTX. `level_tiles()`: the block height of a level `rows` block-rows high
(`runtime/nvn/nvn_tex.c`, `adj_tile`): halved while it is too tall. `block_linear()`: the offset of each 16-byte piece
(row, piece) of a level, in the Switch 2 GOB order.

### `bc4_encode()`

BC4 blocks of an L image: each block's lowest and highest value as the ends, every pixel the nearest of the eight
levels between them.

### `astc_block()`

One 128-bit block of 16 RGBA texels: the two ends of the colours' main direction, every texel its nearest of the four
steps between them.

The block is ASTC 4x4, one partition, endpoint mode 12 (RGBA, direct), 8-bit endpoints and a 4x4 grid of 2-bit weights
(`ASTC_WEIGHTS`): 11 bits of block mode (0x042: weights 0..3, grid 4x4), 2 of partition count, 4 of endpoint mode, then
the eight endpoint bytes from bit 17 (r0 r1 g0 g1 b0 b1 a0 a1) and the 32 weight bits from bit 127 down. The 79 bits
left after the mode and the weights hold eight values of 0..255 exactly, so the decoder reads the endpoints as plain
bytes. The ends are swapped when the second is the darker in RGB: the decoder would read them the other way (blue
contraction).

### `fit()`, `bleed()`, `mask_of()`

`fit()`: the image's opaque part scaled to fit `box` (x0, y0, x1, y1) and centred in it, on a transparent canvas of
`size`; resampled with premultiplied alpha, so the edges keep their colour. `bleed()`: the colour of the nearest
covered pixel spread under transparent ones, so a compressed block that holds both (covered and transparent pixels) ends in the button's own colour
rather than in black. `mask_of()`: the action prompt's mask of a dark picture: the white letter or symbol inside it,
or for a mouse, whose white is the pressed button rather than a label, the mouse itself with that button cut out.

### `draw_textures()`

Paints the action prompt's letters (from `glyph`) and the ocarina's note buttons (from `note`; both Switch button to
picture) into the BNTX data (a bytearray) in place. A new letter takes the height and centre of the game's own letter
in that mask (a wider one may use a little more width); a note button fills `NOTE_BOXES`.

### `write_overlay()`

`outputs`: RomFS path to new file bytes; `originals`: RomFS path to the original's bytes. Writes each file under `out`
and the manifest `runtime/hle/romfs.c` `overlay_load()` checks: path, size, SHA-256, the original's SHA-256.

### `default_binds()`

The current settings file, or an existing older one (`nx2navi.ini`) when that is all the folder has.

## `tools/perf_summary.py`

Condenses the `NX2SARIA_TRACE=perf` and `NX2SARIA_TRACE=sched` lines of a game log over a frame window:

```
python tools/perf_summary.py build/v121/logs/fight.log 1560 2600
```

`mem: dirty` lines (the dirty census of `runtime/vk/vk_memory.c`) are summarised per pool class (CPU_CACHED,
CPU_UNCACHED, other): what a device-local mirror of buffer-bound pools would upload per frame and per submit,
FlushMappedRange use, mirror size.

The present side (`runtime/vk/vk_backend.c` `present_main()`): the `present:` lines of `NX2SARIA_TRACE=present` give
percentiles of the host present's interval, its paced wait, how far past its target it went, the present call and the
presenting thread's hand-off wait (the last two only in logs that have them), and the `perf: present thread` lines of
`NX2SARIA_TRACE=perf` the present thread's averages per window. The render thread's hand-off share is read from the
perf lines that have it.

The text above, as the tool prints it when run without a log, is the string `USAGE`.

### `dirty_fields()`, `pct()`

`dirty_fields()`: the `key a/b/c` and `key x` pairs of a `mem: dirty frame` line, as key to list of floats. `pct()`:
the q quantile of the values (nearest rank below), 0 for none.

### `present_summary()`

`pres`: field to milliseconds of the window's `present:` lines; `wins`: the fields of the `perf: present thread`
lines. Its `avg()` is the present-weighted mean of a window average.

### `dirty_summary()`

`lines`: frame and fields of the window's lines; `frames`: per-frame eager KiB triples. Its `avg()` is the
frame-weighted mean of a per-frame value.

## `tools/pgo.py`

Merges the raw profiles of an instrumented build into the execution profile a build compiles with
([building.md](../building.md), "Profile-guided build").

```
python tools/pgo.py merge <game folder> --version v111 --toolchain C:\msys64\ucrt64
python tools/pgo.py merge build/v143-pgogen --version v143 [--out build/pgo/pgo-v143.profdata]
```

An instrumented build (`tools/make_game.py --pgo gen` for game 1.1.1, `tools/build_game.py --pgo gen` for the other
versions) writes `<build>/pgo/default_<id>.profraw` while the game runs (every minute and at exit); successive runs of
the same exe add to that file. llvm-profdata must come from the toolchain the instrumented build was compiled with
(`--toolchain DIR`, its `bin/llvm-profdata`): the raw format is tied to the compiler's version. The merged file is
read by the compilers of the builds that use it; one of the same LLVM release reads it, an older one may refuse it,
which `tools/make_game.py` finds out with a trial compile before it uses the file (`pgo_trial()`).

Beside the profile goes `<out>.json`, the training record: the game version, `recomp/` at the merge as its git tree
(`recomp_tree()`) and by content (`recomp_digest()`, which a kit without git compares: `tools/make_game.py`
`pgo_record()`), and the tool that merged. The profile matches the generated C of that generator, since functions are
matched by name and control-flow hash and a regenerated function silently loses its counts. `tools/make_game.py`
therefore compiles with a profile only while `recomp/` is the recorded one, and `tools/make_launcher.py --pgo` says so
when it is not. Merge right after the training runs, from the commit they were built at: a game folder made by
`make_game.py --pgo gen` names the `recomp/` it was built from (`pgo/training.json`), and the merge stops when the
checkout holds another.

`DEFAULT_DIR` is where `tools/make_game.py` and `tools/make_launcher.py` look.

### `llvm_profdata()`

llvm-profdata of `--toolchain`; without one the newest llvm-mingw under `toolchain/`, else MSYS2 UCRT64's, else the
one on PATH.

### `recomp_tree()`, `recomp_digest()`

`recomp_tree()`: the git tree id of `recomp/` at HEAD; `None` when `recomp/` has uncommitted changes.
`recomp_digest()`: `recomp/` by content, as a kit without git works it out too: the lifter's code and the version's
patch table (for v111, `tools/make_game.py` `recomp_digest()`).

### `training()`

What the instrumented game in `build` was made from (`pgo/training.json`, `tools/make_game.py` `pgo_gen_record()`),
`{}` for a build that wrote none (`tools/build_game.py`). A game built from another `recomp/` than this checkout's, or
for another game version, stops the merge: the record would name a generator the counts were not gathered on.

### `llvm_release()`

The LLVM release a `--version` line names, `''` when it names none.

### `fitting()`

The record beside a profile, for a release from this checkout. A profile whose record does not name this checkout's
`recomp/` stops the release: the builds made from it would leave the profile out (`tools/make_game.py`
`pgo_record()`), and the release would carry it for nothing.

### `place()`

Copies a profile and its record into a release's `data/` as `pgo-<version>.profdata` and `.json`, where the builds
made from that release look for them (`tools/make_game.py` `pgo_file()`). Returns the path of the profile's copy.

## `tools/pipeline_list.py`

The shared pipeline list: graphics pipelines players met, for an install to build before play
([building.md](../building.md) has the steps).

```
python tools/pipeline_list.py merge OUT.bin GAME_DIR_OR_LIST [GAME_DIR_OR_LIST ...] [--mesh-only]
python tools/pipeline_list.py info FILE_OR_GAME_DIR [...]
```

A game folder records every graphics pipeline a run builds in `pipeline-keys.bin` (`runtime/vk/vk_pipeline.c`, its
pipeline keys: the pipeline state with its shaders named by input id) and every shader variant in `shader-answers.bin`
(`runtime/gfx/gfx_shader.c`, its answers met in play: stage, code hash, input id, translator answers). The next start
of that folder builds its recorded pipelines ahead of play; another install, or the same one after its caches were
removed, meets each of them in play first. A mesh pipeline met that way is compiled then, 0.2 to 1.1 s with its draws
left out of the picture: all of it where mesh pipelines have no stage libraries, and otherwise the library of its task
and mesh stages, which is most of it and which only a pipeline record names (`runtime/vk/vk_pipeline.c`, the mesh
pipelines' stage libraries ahead of their draws).

This tool folds the two files of any number of game folders into one list file; a list file made before can stand in
for a folder, so a list grows by the folders played since. Beside the shader variants the pipelines name, the list
takes the compute variants each folder dispatched: no pipeline record names a compute shader, and a variant with other
answers than the shader list's default one was translated in the middle of play, 30 to 40 ms on the frame that first
dispatched it. `tools/prepare_shaders.py` reads the list beside the shared shader list: the shader variants it names go
into the seed, so the preparation translates them, and its pipeline records go next to the game as
`seed-pipeline-keys.bin`, which every start of the game counts as recorded pipelines beside its own
(`runtime/vk/vk_pipeline.c` `keys_open_seed()`), so a new install builds them before play, and which
`nx2saria.exe --prepare-shaders` (and `--prepare-pipelines` on a folder that is prepared already) builds once into the
pipeline cache and the graphics driver's own.

What a record depends on. Its shaders are named by input id, a hash of the game's shader code and the answers, which
no translator, GPU or driver changes: a record made on one machine names the same shaders on another with the same
game version. Its state is the game's (formats, blend, depth and stencil, topology, sample count) and a few choices of
the runtime's settings (a culled foliage shadow pass, the depth range); everything that depends on the GPU is derived
from it when the pipeline is built. A record whose state this install never reaches costs one pipeline in the caches,
and one whose shader this game version lacks is left out by the preparation. The record layout belongs to the runtime
that wrote it (`KEYS_VERSION` and the record size, in the file's header): a list is made again for a runtime that
changes either, and the runtime ignores one that does not match.

The list is derived from game data: it stays out of the repository (`tools/check_content.py` refuses it) and travels
with the installer archive as `data/pipeline_list.bin`, as the shader list does.

File: `"NX2NPLST"`, version u32, answers bytes u32, keys bytes u32, then a `shader-answers.bin` image (header, the
records the keys name and the compute variants', input id kept) and a `pipeline-keys.bin` image (header and records).

`ANS_REC` is the answers record of `runtime/gfx/gfx_shader.c`: stage, code hash, input id, answers, pad.
`STAGE_NAMES` follows `GFX_STAGE_*` of `runtime/gfx/gfx.h`.

### `read_answers()`, `read_keys()`, `key_ids()`, `read_dir()`

`read_answers()`: a `shader-answers.bin` image to its records (bytes each); `[]` for another magic or record size.
`read_keys()`: a `pipeline-keys.bin` image to magic, version, record size and records; records `[]` for a file too
short. `key_ids()`: the input ids a key record names: vertex (or mesh), then fragment and task when it has them.
`read_dir()`: a game folder's recorded keys and answers; a missing file gives no records. A list file gives what it
holds.

### `merge()`

One list from the folders' files (or earlier lists): each key record once, the answers record of every shader they
name and, unless `mesh_only`, of every compute variant a folder dispatched. A key naming a shader the folder's answers
do not name is counted as lacking and left out: another install could not translate it.

### `unpack()`

A list file to its answers records and its `pipeline-keys.bin` image; `None` when it is not one.

## `tools/prepare_shaders.py`

Prepares the default variant of every game shader and the variants of the shared shader list for a build, once, before
play ([building.md](../building.md)). `tools/make_game.py` `step_key()` puts this file's SHA-256 into the key of its
shaders step.

```
.venv-py314\Scripts\python tools\prepare_shaders.py build\v121 [--version v121] [--list <tsv>] [--no-run]
                                                 [--romfs DIR --exefs DIR]   # instead of build\extracted\<version>
```

The list (`tools/shader_list.py`) names shader variants players met: a shader key (SHA-256 of the NVN control section
and code, as `tools/shader_census.py` names shaders) and the translator answers it was translated for. This tool reads
the shaders from the extracted RomFS and ExeFS (`tools/shader_census.py` `inventory()`), keeps the list's variants
whose shader is in this game version, adds each shader's default variant (every texture slot a 2D texture, float
vertex inputs and colour outputs: the default bind state), and writes them next to the build's `nx2saria.exe` in the
record layouts of `runtime/gfx/gfx_shader.c` (its answers met in play):

```
seed-programs.bin  "NX2NSPRG": stage, length, c1 length, runtime code hash, control section, code, c1
seed-answers.bin   "NX2NSANS": stage, code hash, input id (zero: the runtime computes it), answers, priority
```

Priority (the pad byte): 0 shaders the list's warm rows flag as title/menu (t), 1 other warm rows (S, C, R), 2 the
rest; a default variant takes its shader's priority and sets `DEFAULT_FLAG` (bit 7). The runtime reads a flagged
record's first translation and translates it again with better answers where it reads other ones
(`runtime/gfx/gfx_shader_guess.c`): integer vertex inputs, and the texture and image types a compute shader's
translation declares, for which a compute default variant goes without texture answers. Then it runs
`nx2saria.exe --prepare-shaders`, which translates every record into the build's shader cache, writes
`shader-prepared.bin` (one record per variant, in priority order) and builds every variant's stage library or compute
pipeline once, so the GPU driver's own disk cache holds them (`runtime/vk/vk_pipeline.c`, the stage library prebuild).
The seed files can be deleted afterwards.

The shared pipeline list (`tools/pipeline_list.py`: graphics pipelines players met, with the shader variants they
name) is read beside the shader list when there is one: `tools/data/pipeline_list.bin` (`BUNDLED_PIPELINES`; out of the
repository, as `BUNDLED_LIST`), `data/pipeline_list.bin` in a release folder, or `--pipeline-list`. Its variants of
shaders this game version has join the seed with priority `LIST_PRIORITY` (with the warm-up rows), and its key records
are written as `seed-pipeline-keys.bin`, which `--prepare-shaders` builds into the pipeline caches once the seed is
translated (`runtime/vk/vk_pipeline.c`, the shared pipeline list; mesh pipelines by default). That file stays in the
build directory: `nx2saria.exe --warm-shaders` and `--prepare-pipelines` build from it again after an update or a new
driver. A `seed-pipeline-keys.bin` of a list this build no longer has is removed.

A driver whose shader compiler crashes on a variant crashes on it in every run (NVIDIA 615.78.08 on an RTX 5080, issue
#30). The translations and `shader-prepared.bin` are written by then, and the journal the run leaves (`JOURNAL`: a
64-byte slot per worker, input id first) names the variants the driver was building (`runtime/vk/vk_pipeline.c`
`skip_init()`), so only the driver step runs again (`nx2saria.exe --warm-shaders`), up to `RETRIES` times, and skips
them.

Game-derived output stays in the build directory (ignored). The list is read at preparation time from
`shader_list.tsv` in the tools' `data` folder when that file exists (`BUNDLED_LIST`: the installer archive bundles a copy, which has no
git and no `refs/`; it stays out of the repository), else from `refs/` through git with the rows its history dropped
(`tools/shader_list.py`); nothing of it is copied into the repository. It needs Python 3.14 (`compression.zstd`), so
it runs in `.venv-py314` or the embeddable 3.14. The three imports after the `sys.path` line carry `# noqa: E402`,
which stays.

The constants: `STAGES` follows `GFX_STAGE_*` of `runtime/gfx/gfx.h`; the format names are `fmt_names` of
`runtime/gfx/gfx_shader.c`; in `DEFAULT`, answers outside a shader's use mask are dropped.

`SLOW_UNUSED` (source suffix, code bytes above which) names the default variants left out unless `--all-shaders`: the
larger compute programs of two of the game's three NDSR upscaler packages. The translator turns their 20-47 KB of code
into 3-12.6 MB of SPIR-V, which the GPU driver took 34 s to 44 min each to build (RTX 5090, driver 621.01): 35
programs, the 24 that translate took 19,400 of the 21,750 s every compute variant together took. Play sessions met
none of them that was slow to build (one 20.8 KB program built in 0.2 s), while all five `agl_ndsr_vr_light.pck`
programs play met took 77-153 s each, so that package stays whole. A program play does meet here is translated and
built at its first use, as before the NDSR packages were read at all.

### `read_pipeline_list()`

Answers records and `pipeline-keys.bin` image of the pipeline list at `path`, or of the bundled one; `None` without a
list. A file that is not a list stops the run: a release that names one must not go on without it.

### `list_variants()`

Seed records for the pipeline list's shader variants: those whose shader (runtime code hash) is in `have` and whose
(hash, answers) the seed does not hold yet. The input id is left zero, as for every seed record: the runtime finds it,
and finds the id the list's key records name, since it depends on the code and the answers alone.

### `pipeline_variants()`

The vertex and fragment variant names of an R/B row's pipeline key. Since its revision of 2026-10-28 the list keeps
keys packed, `<vs variant>:<fs variant>:<the rest in hex>`; older revisions and contribution files hold the whole key
in hex, `<vs variant>\0<fs variant>\0` and a Metal descriptor.

### `parse_list()`

V rows as (key, deps); priority per shader key from the warm rows (variant names start with the key).

### `answers()`

`GfxShaderAnswers` in the layout of `runtime/gfx/gfx_shader.c` `pack_answers()` (147 bytes) from the list's deps JSON.
A texture answer `*` is any kind, translated as the plain 2D it stands for. The local size is zero for vertex and
fragment programs, as `runtime/vk/vk_exec_draw.c` `answers_for()` has it (they are in the input id). For compute, task
and mesh it is the three words at the control section's local size (NVN2 at +0x58), 0 read as 1, each cut to 16 bits
as `answers_for()` stores them (task and mesh programs keep other fields there).

### `nvn2()`

An NVN2 (Switch 2) control section as `tools/shader_census.py` `nvn2_stages()` keeps it: 0xe0 bytes, zeros to 0x880.

### `bounds()`

The c1 offset and the length as `runtime/gfx/gfx_shader.c` `req_init()` takes them. NVN2: play hands `req_init()` the
code size of `runtime/vk/vk_exec_draw.c` `ctl_stage_len()`, which reaches the end of the c1 constants only when there
are some (+0x40 below +0x44). With an empty c1 range past the code the length is the code size alone; cutting at the
range's end (as `tools/shader_census.py` does) seeded most of the game's vertex programs under keys play never asks
for.

### `code_hash()`

As `runtime/gfx/gfx_shader.c` `build_code_hash()`.

### `driver_crashed()`

The game died while the graphics driver built variants: the journal it left names at least one.

### `main()`

A missing list row says nothing about the walk: the list covers several versions, and 1.1.0 holds 17,587 of its
41,414 rows, so most rows are absent because the game does not have them, not because the walk missed them. A walk
that found next to nothing does say something: the shader directories have moved. So when fewer than 64 shaders, or
a twentieth of the listed variants, were found, every RomFS file is read instead.

A default variant that equals a list row of the default bind state is not written twice. The records are sorted by
priority with a stable sort: list order within a priority.

## `tools/prof_report.py`

Report for a `NX2SARIA_PROFILE` sampling profile (`runtime/diag/prof_win.c`): top functions and the split between
guest, runtime and outside.

```
prof_report.py <profile> <nx2navi.map | nm -n output> [--top 40] [--chains 30]
```

The map is the one from the link (`build/<version>/nx2navi.map` from lld, whose addresses are RVAs, or a GNU ld map
such as the launcher's `build-cache/ocarina.map`, whose addresses include the image base); the profile header carries
the runtime image base, so ASLR does not matter. Symbols in the map are labels without sizes: a Rip belongs to the
nearest symbol at or below it. A map lists global symbols only, so a static function's time lands on the global
function before it: the output of `nm -n <exe>` in the map's place names the static functions too.

A profile taken with `NX2SARIA_PROFILE_RENDER=1` or `NX2SARIA_PROFILE_CHAINS=1` also has call chains: the report then
adds the inclusive time per function (a function counted once per chain), and for each module outside the exe the exe
functions that call into it and the longest common chains down to it.

The three patterns: `SYM` is an lld map line whose In column is empty (object lines have a `path:(section)` there);
`SYM_LD` a GNU ld map line: the address, then the name, no size; `SYM_NM` a line of `nm -n` of the exe: code symbols,
static ones too. `load_map()` leaves out the `.text` section nm lists for each object.

### `report_chains()`

Where running threads are: the innermost exe frame of each chain that does not end in a wait. A chain whose leaf is in
ntdll, win32u or KERNELBASE is taken as blocked, which also drops the few running samples inside them (clock reads); a
leaf in another module (the driver, the C library) is charged to the exe function that called it. Then, per outside
module, the innermost exe frame of each chain whose leaf is in that module.

### `main()`

The map's addresses include the image base (0x140000000 for an x64 exe); a runtime Rip is an offset from wherever the
loader put the image. The lowest map address aligned down recovers that base, so a Rip becomes a map address by adding
it back. The comment said the address is aligned down to 64 KiB; the mask in the code, `~0xFFFFF`, aligns it down to
1 MiB.

Flat samples are named by `sym_at()` as the call chains are: right for a map with or without the image base. The
samples outside in ntdll, win32u and KERNELBASE are waits and message loops, threads not running, and count as idle.

## `tools/prompt_art.py`

The button art `tools/pad_prompts.py` draws the button prompts from: the pictures of each pad style (`STYLES`), the
keyboard and mouse folders (`KM`), and `art_files()`, the files a release carries so the build can draw the prompts on
the player's PC (`tools/make_launcher.py` and `tools/make_kit.py` with `--prompt-art`, the prompts step of

`tools/pad_prompts.py`, the digest `PROMPT_TOOLS` records takes this file's code lines as written, so its three
comments at the end of code lines stay for now.

The art is 128x128 PNGs in the folders of button prompt art packs: `XGamepad/Default` and `/Light`,

- `steamdeck`: the Steam Deck's own labels, from the two pads' pictures (the packs have no Deck style): A B X Y where

- `KM`, the keyboard and mouse: a key in each shade (`Dark`: a dark key with a white label, the button font and the

The stick pictures of one style: `<stick>_<direction>` for L and R.

### `overlay_folder()`

The game folder's overlay folder of a style (`pc` for the keyboard and mouse) and pad layout (`position` or `label`),

## `tools/release_files.py`

The checks and the page text of a release that GitHub Actions builds and publishes (`.github/workflows/release.yml`;
[releases/README.md](../releases/README.md)). Standard library only: it runs with the runner's own Python, before
anything is installed. Each command prints what it found, one line per finding, and exits 1 on a problem.

- `python tools/release_files.py body --tag T --notes docs/releases/T.md --state prerelease|stable [--repo o/n]`: the

`PRERELEASE_LINE` is the pre-release line of the notes ([releases/README.md](../releases/README.md), "The notes"): a

### `text()`

A text file's content with LF line ends, as git checks it out on Linux (`.gitattributes`: `eol=lf`).

### `version_key()`

The order of release tags as semver orders their versions: v0.19.0-rc.1 < v0.19.0-rc.10 < v0.19.0.

### `check_promote()`, `check_tag()`, `check_files()`

Each returns its findings and raises `Problem` otherwise. `check_promote()`: when the tag may be made the stable
release beside the stable releases' tags; tags that are not release tags (none so far) are left out. `check_tag()`:

## `tools/rename_legacy_names.py`

Renames the `NX2NAVI_*` setting names still written in the code to their current `NX2SARIA_*` spelling
([branding.md](../branding.md)).

python tools/rename_legacy_names.py --check   print what would change; exit 1 when anything would
```

The game, the launcher and the build tools read every setting under both names, `NX2SARIA_*` first

- `tools/vendor/` (kept byte-identical to its source) and `runtime/third_party/`;

## `tools/romfs_check.py`

Checks every file of a player's packed game data, and stands in for the damaged textures it can
([launcher.md](../launcher.md), "Check the Game Files"). `tools/make_game.py` records a digest of this file's code as
`SCAN_TOOL`, and `tests/launcher_test.py` compares it; the digest takes each code line as written, so the one comment
at the end of a code line stays in this file until the digest is next changed for another reason.

```
python tools/romfs_check.py --game FOLDER [--romfs FOLDER] [--mods FOLDER] [--jobs N]
```

A dump can hold files whose first pages are zeros, with a container checksum that still passes because the damage was
packed along with them. The game then cannot decompress such a file, opens it over and over and gives up on everything
that needs it: one damaged normal map left a whole room without walls. Nothing during play looks for this, so the game
build runs this once for each copy of the game data (`tools/make_game.py` `step_scan()`).

Every `.zs` file of `<game>/romfs` (`index.json` and `romfs.bin`, as `tools/make_game.py` writes them; `--romfs` names
another) is decompressed in full, with the dictionary its frame names from `Pack/ZsDic.pack.zs`. A file of any other
kind that is nothing but zeros is reported too. The result goes to `<game>/romfs-check.json`.

A damaged `Tex/<name>.bntx.zs` is replaced by a stand-in: an undamaged texture of the same kind, the closest name with
the same length, with the name inside it changed, so the game loads it and what uses it appears. It is another
texture, not the original, and only a clean dump restores the original. The stand-ins are an ordinary mod folder
(`--mods`, default `<game>/mods`) named `STANDIN_MOD` that the Mods menu can turn off; it is removed again when nothing
is damaged. They are built from the player's own files on the player's machine and never enter the repository.

It needs zstandard (`tools/requirements-launcher.txt`).

`PIECE` is how much of a file the decompressor is given at a time. Each call returns its output as one bytes object,
which the library grows as the output comes: with 4 MiB of input a call's output is tens of MiB, grown by copying, and
the copying holds the interpreter's lock, so the worker threads wait on each other. Measured on 32 MiB frames with 12
threads: about 120 MB/s of packed data with 4 MiB pieces, about 2,500 MB/s with 64 KiB pieces; files smaller than a
piece are the same either way.

### `sarc_members()`

Name to start and end of the files of a SARC archive.

### `Image`

The packed game data; each thread reads through its own handle. `Image.decompressor()`: one per thread and
dictionary, as a decompressor is not for two threads at once.

### `problem()`

Why the file is damaged, or `None`. A frame naming a dictionary the game does not have cannot be judged: `None`. Once
the decompressor reports the end of the frame, the frame is whole: bytes after it are not the frame's, whichever piece
they fall in.

### `donors()`, `stand_in()`

`donors()`: undamaged textures whose names have this one's length, most alike first; the same last word is worth
most. `stand_in()`: a compressed stand-in for the damaged texture at `path`, or `None` when no undamaged texture can
be renamed to it.

## `tools/romfs_index.py`

Builds the RomFS index the runtime binary-searches (`runtime/hle/romfs.c`) and its `romfs_config.h`. Standard library

### `write_placeholder()`

`romfs_config.h` without a RomFS (no extracted game on this machine): the game builds, and `fs_init` stops with a
named fatal.

## `tools/run_game.py`

Runs a build of the game unattended on a copy of the user's profile with a backed-up save and scripted input
([performance.md](../performance.md), [controls.md](../controls.md), [boot-to-map.md](../boot-to-map.md)).

The profile is never written: each run copies it to `<exe dir>/prof-<tag>`, swaps in the save backup, and deletes the
copy afterwards. It is the game folder's own profile when there is one (`<exe dir>/profile`, a folder
`tools/make_game.py` built), else `build/profile`. The log records how many other copies of the game and of Ninja ran,
because timings taken next to them are not comparable.

```
python tools/run_game.py build/v143 --save <backup> --seconds 15 --tag idle --env NX2SARIA_TRACE=perf
python tools/run_game.py build/v143 --save <backup> --script <input.txt> --seconds 18 --tag fight --quiet \
    --env NX2SARIA_TRACE=perf,sched
python3 tools/run_game.py <game folder> --save <report.zip> --seconds 600 --wall 90 \
    --env NX2SARIA_SHOT_DIR=shots --env NX2SARIA_SHOT_AFTER=40 --env NX2SARIA_SHOT_EVERY=10
```

`<backup>` is a folder of `build/save-backup` or of the profile's `save-backup` (the game keeps its last three saves
there), or a save folder or `.zip` from elsewhere, such as a crash report's zipped profile folder; `--script` defaults
to `tools/input/load_save.txt` (title screen to the first save slot), and a recording made with
`NX2SARIA_INPUT_RECORD` replays the same way. `--wall` ends a run whose script never reaches the world clock;
`NX2SARIA_SHOT_EVERY` takes its pictures by wall time.

`--boot-map <area>[:<start position>]` starts the game in that area from the save without the title screen or the file
menu (`runtime/patches/boot_map.c`), with `--boot-map-slot`, `--boot-map-age` and `--boot-map-time` beside it. Its
input script defaults to `tools/input/boot_map.txt`, which presses nothing. The run fails (exit code 3) when the log
has no "boot map: arrived in" line for the area asked for; the boot map's lines are printed at the end.

```
python3 tools/run_game.py <game folder> --save <backup> --boot-map HyruleField_Child:HyruleField_FrontOfMarket \
    --boot-map-time 21:00 --seconds 10 --wall 180 --tag field-night
```

- The import of `launcher/saves.py` carries `# noqa: E402` with its reason (Import Saves' search, for a save from
  elsewhere), which stays.
- `LOCK_OFFSET`: the Windows byte-range lock sits past the holder text, so other processes can still read it.
- `MAX_RUNS` (3, or `NX2SARIA_MAX_RUNS`): more parallel runs exhaust device memory (16 GB RX 9070).
- `GAME_EXES`: the game's executable as each tool names it: `tools/build_game.py`, `tools/make_game.py` on Windows,
  `tools/make_game.py` on Linux, `tools/build_game.py` on Linux.

### `count()`

Running processes of this executable name. On Linux it reads `/proc/<pid>/comm`, the process name cut to 15
characters; a process that ended while the list was read is skipped.

### `keep_in_background()`

Pushes the game window behind the user's windows as soon as it appears, for builds older than
`NX2SARIA_BACKGROUND_WINDOW`: `SetWindowPos` with `HWND_BOTTOM` and `NOSIZE | NOMOVE | NOACTIVATE`.

### `take_slot()`, `try_lock()`

`take_slot()` blocks until one of `MAX_RUNS` run slots is free and holds it (a locked file) until this process exits.
`try_lock()` takes an exclusive OS lock on the open file without blocking; false if another process holds it.

### `take_gpu_lock()`

Blocks until this process holds the machine-wide measured-run lock (`build/.gpu-run.lock`) and returns the open file.
The OS drops the lock when the process exits or dies, so a stale file never blocks. The file text names the holder
(pid and build path) for the waiters.

### `save_source()`

Folder, slot and names to leave out, of the save to run. A backup named in `build/save-backup` or the profile's
`save-backup` is a whole save: a bare name is a backup's name, a path is searched. A folder or `.zip` from elsewhere
(a crash report's zipped profile folder, a game folder, an emulator's save) is searched as the launcher's Import Saves
searches it; `slot` names the one slot it holds, `None` for a whole save. `zipfile` leaves out absolute paths and `..`
parts when the zip is unpacked.

### `profile_copy()`

`save-tx` is removed from the copy: a finished or interrupted commit there would be loaded in place of the save
swapped in (`runtime/hle/fs_host.c`).

### `boot_map_report()`

Prints the boot map's lines of the run's log; returns 3 in place of a clean exit when Link did not arrive in the area
asked for (`runtime/patches/boot_map.c` `boot_map_tick()` writes the line).

### `main()`

Without `--show` on Windows the game gets `NX2SARIA_BACKGROUND_WINDOW=1`: SDL windows open in front either way.

## `tools/runtime_folders.py`

The runtime's files by subsystem folder: which file of `runtime/` moved from the top level into which folder, and the
script that made the move and rewrote the paths that name the files ([architecture.md](../architecture.md)).

```
python tools/runtime_folders.py move              # git mv every file of FOLDERS from runtime/ into its folder
python tools/runtime_folders.py rewrite [FILE...]  # runtime/<name> -> runtime/<folder>/<name> in those files
python tools/runtime_folders.py where NAME...      # the path below runtime/ a file has now
python tools/runtime_folders.py table              # the table as Markdown
```

`rewrite` without files takes every tracked file outside `runtime/`, `tools/xlate/` and `tools/vendor/` that names one
(git grep) and changes `runtime/<name>` and `runtime\<name>` in any text, and in Python a path joined from a runtime
folder, such as `ROOT / 'runtime' / '<name>'` or `rt / '<name>'`. A branch made before the move takes a rebase as
usual (git follows the renames); a file it adds that names a moved one is brought up to date with `rewrite <file>`,
and a C file it adds at the top of `runtime/` still builds there, as the top level is compiled as before.

The files that stay at the top of `runtime/`: the entry point, the guest's core (`cpu.h`, `simd.h`, `simd_fp.h`,
`dispatch.h`, `host.h`: the lifted C includes them, and its compile has only `runtime/` on its path), the loader,
guest memory, the log, `cfg.h` (`runtime/platform/win32.c` includes it as `../cfg.h`), the small shared helpers and
the Windows resource files.

- `VK_EXTRA`: the rest of `vk_*`, and the headers of the Vulkan back end that carry another name. `FOLDERS['vk']` is
  `vk/` as it was on the day of the move (the `vk_*` files then); a `vk_*` file added later stays where it is put.
- `TEXT` matches `runtime/<name>` and `runtime\<name>` as a whole name (not `vk_fsr.c` inside `vk_fsr.cpp`; a full
  stop after it may end a sentence). `JOIN` matches a Python path join that ends in a
  moved name, from a runtime folder: `... / 'runtime' / 'name'`, `rt / 'name'`.

### `move()`

git mv of each file of `FOLDERS` from the top of `runtime/` into its folder.

### `rewrite()`

The translator's sources are left as they are (`tools/build_xlate.py` hashes them into the translator's identity), as
is the vendored code.

## `tools/sdl3_pin.py`

SDL3 for a Linux build on a system that has none: the headers and `libSDL3.so.0` a build kit carries
([README-BuildKit.md](../README-BuildKit.md)). Standard library only: the build kit's Python runs this.

```
python tools/sdl3_pin.py [--dest toolchain/sdl3] [--deb FILE FILE | --sysroot FILE]
```

The runtime's window, input and audio are SDL 3. Ubuntu 24.04 LTS and the distributions built on it (Linux Mint 22 and
others on the noble base) package no SDL3 at all, so a build with the system's compiler there found no `SDL3/SDL.h`
(issue #11). This is the SDL3 a kit carries for them, in `toolchain/sdl3`. `tools/make_game.py` takes it where the
compiler finds no SDL3 headers of the system's (`sdl3_choice()`): the runtime is compiled and the game linked against
it, `libSDL3.so.0` goes beside the game (`place_sdl3()`), and the preflight runs a program linked against it, so that
a library it needs and the system lacks stops the build, by name, before the long steps.

It is SDL 3.4.18 as the Steam Runtime 3 builds it, the build the Steam Runtime 3 "sniper" SDK sysroot holds. Built for
the Steam Runtime's glibc (its newest symbol version is GLIBC_2.29), it runs on any distribution at least that new. It
links the desktop's client libraries directly instead of loading them when it starts: libX11, libXext, libXcursor,
libXi, libXfixes, libXrandr, libXss, libXtst, libxkbcommon, libwayland-client, -cursor and -egl, libdecor-0, libpulse,
libasound and libfribidi, all of which a desktop install of Ubuntu or Mint has.

The files come from one of two places, checked either way:

- the runtime's apt pool: the packages libsdl3-0 (the library) and libsdl3-dev (the headers), 2.7 MB, each checked
  against its SHA-256 (`DEBS`: package to address and SHA-256). The pool keeps the current version of a package only,
  so these go once the Steam Runtime moves on;
- then the dated snapshot of the sniper SDK sysroot that holds the same build (`SYSROOT`: the snapshot with libsdl3-0
  and libsdl3-dev `DEB_VERSION` installed), 1.2 GB, read as it downloads and checked against its SHA-256 at the end,
  nothing of it written to disk but the files below.

Both must give exactly the files `CONTENT_SHA256` names (`content_digest()` of the kept files, `pinned.txt` aside: the
86 headers, the library and the copyright file), so the kit's SDL3 is the same from either.

Kept: `include/SDL3/*.h`, `lib/libSDL3.so.0` (the library's file under its soname), the package's copyright file
(`SDL3-copyright.txt`: SDL is zlib, and the file names the licences of the parts it contains) and `pinned.txt`.

- `VERSION`: SDL's own version, as `SDL_version.h` defines it. `DEB_VERSION`: the packages' version in the Steam
  Runtime 3 apt pool.
- `FOLDER`: below a checkout's or a kit's root: `include/`, `lib/`, the copyright file. `STAMP`: in the folder, the
  packages' version, written last. `LIB`: the soname the game is linked against and finds beside itself.
- `HEADER` and the patterns beside it: members of a package's data archive or of the sysroot that are kept; `HEADER`'s
  file name part takes no `..` and no folder, so nothing is written outside the folder. `NEAR`: files a kept member
  may be a hard link to: SDL3's own, a few MB, held while an archive is read.

### `have()`

True when the folder holds the pinned SDL3, complete (the stamp is written after the last file). A stamp that is not
ASCII (`ValueError`) is no stamp.

### `kept_name()`, `take()`

`kept_name()`: where a member of the packages or the sysroot goes in the folder, `None` when it is not kept. `take()`:
the kept members of an open tar archive into `kept` (folder path to bytes). A kept member that is a hard link to one
of SDL3's files read earlier (`NEAR`) takes that file's bytes; symbolic links are not followed (the library is taken
by its own file name).

### `deb_data()`, `deb_files()`

`deb_data()`: name and bytes of the data archive of a Debian package: an ar archive whose `data.tar.*` member holds
the files. Members start on even offsets. `deb_files()`: the kept files of a Debian package (bytes) into `kept`; the
pinned packages are xz, as the Steam Runtime's dpkg writes them.

### `content_digest()`

One SHA-256 over the kept files' paths and SHA-256s: equal for two sources that gave the same files.

### `clear()`, `write()`, `unpack()`

`clear()` removes what an earlier unpack wrote into the folder, and nothing else of it. `write()` puts the kept files
into the folder, after they are checked: complete and exactly the pinned ones. `unpack()`: the headers, the library
and its copyright file of the two packages (name to bytes) into the folder.

### `HashingReader`, `sysroot_files()`

`HashingReader`: a file object over a download that hashes what is read through it and counts it. `sysroot_files()`:
the kept files of the sysroot archive read from `f` (a download or a file), checked against `SYSROOT`'s SHA-256 once
all of it is read; what follows the archive's end marker is read too, for the hash.

### `download()`

The bytes at `url`, `None` when the server or the network does not give them.

### `resolve()`

The folder holding the pinned SDL3 (default `<root>/toolchain/sdl3`), fetched and unpacked there when it does not hold
it yet. `debs`: the two packages on disk instead of the download, in any order, each one of the pinned files;
`sysroot`: the sniper SDK sysroot archive on disk. Returns the folder: `include/` goes on the include path,
`lib/libSDL3.so.0` into the link.

### `header_version()`

Major, minor and micro as `SDL_version.h` defines them in `text`, `None` when it does not.
