# NX2Saria 0.18.3 in detail

The option names, log lines and measurements behind the [0.18.3 release notes](../releases/v0.18.3.md).
How to install or update is in [the install guide](../install.md). The design and the measurements are in
[docs/build-memory.md](../build-memory.md).

## Changed

- **The build starts each compile by the free memory** (#16). It used to size its job count once, at the start, and
  then ran that many whatever happened next.
  - `tools/memgate.py` (new) starts a compile when the memory free now, less what the running compiles may still grow
    into and a reserve (1.5 GiB or 10 % of the RAM, the larger), holds its estimate. At least one compile always runs,
    so a build never waits for ever.
  - Free memory: `MemAvailable` (capped by a cgroup) on Linux; on Windows the smaller of the free physical memory and
    the commit left. Each compile's peak is measured (`wait4` on Linux; on Windows the larger of the peak working set
    and the peak commit) and learned in `build-cache/obj/compile-memory.json`. The estimate is the object's last
    peak +15 % while its source changed little, else a size model scaled by how far it was off.
  - `--jobs` is now the most compiles at once (default: one per processor). `--mem-limit GIB`, `--mem-reserve GIB`,
    `--min-jobs N` and `--no-mem-gate` (or `NX2SARIA_BUILD_MEM_LIMIT`, `_MEM_RESERVE`, `_MIN_JOBS`,
    `_MEM_GATE=off`) adjust it. The AppImage no longer caps the jobs at RAM/4.
  - `recomp/gen.py` closes its chunks by estimated compile cost instead of size (a function that may hold a jump-table
    switch costs size + size²/490,000), and its lift hands out work by the same memory rule. A lift worker killed for
    memory is retried with half the workers instead of hanging the build.
  - **The game is the same:** `tools/lift_compare.py` (new) proves the lift defines every function byte for byte as
    before. Only which file holds a function changes, so this update recompiles the whole game once.
- On Windows the gate counts the commit left, so a PC with a small page file that Windows grows on demand may run
  fewer compiles at once than before: slower, not broken.

## Its log

- The compile step logs the gate's settings, the compiles it held and for how long, the compiles' peak memory
  together, the least free memory, the 5 largest compiles and how close the estimates came.
- The lift logs `emit memory: ...`.
- `memory gate: the compile estimates were not saved (...)` when the estimates file cannot be written; the build goes
  on.

## Tested

- On the Linux bench (16 threads, 31 GiB, 8 jobs, every build from scratch): compile 577 s against 563 s before, the
  compilers' memory together 3.4 GiB at the peak, no compile held. Inside a 6 GiB cgroup limit the lift sized itself
  to 2 workers, 75 compiles were held for 90 s in all, nothing was killed, and the scope peaked at 3.7 GiB.
- On the Windows CI runner, the prebuilt runtime's 165 compiles went through the gate (4 at once, least free memory
  12.0 GiB). The game's own build on a Windows PC has not run yet: this is why 0.18.3 is a pre-release for now.
- Tests: `memgate_test`, `make_game_gate_test`, `build_game_gate_test`, `gen_emit_gate_test`, `gen_partition_test`
  and `lift_compare_test`. An independent review checked the Windows path, that a build always progresses, the
  estimates file and the partition; it found two small issues, fixed before the release (a damaged estimates file or
  one that cannot be written no longer stops a build).
- Not changed, for later: a compile that fails under memory pressure does not record its peak.
