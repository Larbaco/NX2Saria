# NX2Saria 0.21.0-rc.2 in detail

The log lines and tests behind the [0.21.0-rc.2 release notes](../releases/v0.21.0-rc.2.md). How to install or update
is in [the install guide](../install.md). It is the second release candidate of 0.21.0, for launchers on the Preview
channel, and has everything of [0.21.0-rc.1](v0.21.0-rc.1.md) plus the changes below, most of them found in the first
real run of the Linux launcher.

## udmabuf on Linux (#45)

On Ubuntu 24.04 and Linux Mint 22, `/dev/udmabuf` is readable only by root and the kvm group and its size limit is
64 MiB, so the game falls back to shadow copies of its memory. On the bench (Kokiri Forest, the same build, RX 6700)
that is 29.5 fps against 49.5 with udmabuf. The launcher checks this without privilege and, when the module is there
and blocked, Settings offers to fix it: after the player confirms, `pkexec` runs one script that adds a udev
`uaccess` rule and a tmpfiles.d entry setting the limit to 1024 MiB at every boot. The same row removes it. Not offered
on SteamOS or without `pkexec`. Log: `udmabuf: accessible=...; size_limit_mb=...; offer=...` at start, and
`udmabuf: after apply: accessible=...` after the change. The game's own log says which path it took
(`guest memory is a memfd's ... imported as dma-bufs`, or `shadow storage`).

## The Linux install and update (#50)

- Opening the AppImage again over an intact install of the same version starts the installed launcher instead of
  copying it again (`AppImage: <version> already installed`); the menu entry and icon are written only when they
  change, and atomically.
- The AppImage hands its own folder to the launcher, which then finds a dump beside it.
- An update made from the Updates row or `cli.py update` now switches the Linux Python runtime too when its id
  changes; a version that exits with an error within 6 s of starting is rolled back, as on Windows.
- The Linux runtime file is named `NX2Saria-runtime-linux-x86_64-<id>.zip` without the repeated prefix.

## The launcher's log, drives, file choosers and speed (#51)

- `launcher.log` says how the window ended (`window closed by the player on the <screen> screen after N s`, or
  `window ended by SIGTERM`), logs an error in a window callback or a thread with its traceback in `crash.log`, and
  records the first run (`first run: install folder ...`, `dump search: N found ...`), each changed setting
  (`setting: <key> <before> -> <after>`) and each file chooser (`file chooser (zenity): <title>: <path>`).
- Its first line names the kind of install, the distribution, the session type and the desktop on Linux.
- On Linux the dump search also looks at the drives mounted under `/mnt`, `/media/<user>` and `/run/media`, two
  levels deep and for at most 5 s, and the translated folders of `user-dirs.dirs`. File choosers use zenity or kdialog.
- Moving the mouse over a row redraws only what changed (6.4 ms against 55 ms on the bench), and the idle window with
  animations uses less than half the processor it did. On Linux the launcher behind the game no longer reads the
  controller's presses meant for the game.
- The install guide says how to allow the AppImage to run from the file manager.

## Tested

- Linux bench: the AppImage installed twice into a test folder (the second start copies nothing), the launcher
  under Xvfb with the new log lines, the file chooser on a mounted drive, and the dump search on a 1 TB NTFS drive
  (502 folders in 0.3 s).
- Tests: `platform_linux_test`, `launcher_test`, `release_files_test`, `docs_i18n check`.
- Windows builds of each change by GitHub Actions.
- Not tried yet: the udmabuf fix and an update from rc.1 on a player's Linux PC, and the Steam Deck.
