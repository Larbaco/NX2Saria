# NX2Saria 0.21.0-rc.1 in detail

The log lines and tests behind the [0.21.0-rc.1 release notes](../releases/v0.21.0-rc.1.md). How to install or update
is in [the install guide](../install.md). It is the first release candidate of 0.21.0, for launchers on the Preview
channel, and follows [0.20.0](v0.20.0.md).

## The launcher on Linux, installed and updated by the AppImage (#42)

- The AppImage is the Linux installer: run, it installs or repairs the launcher (`launcher/`, the Windows one, with a
  platform layer) under `~/.local/share/nx2saria` with its own Python, and adds an Applications menu entry. The entry
  starts a small installed script that reads `app/current.txt`, so it keeps working after an update and after the
  AppImage is moved or deleted.
- An earlier AppImage install is adopted: the game folder and dump come from `~/.config/nx2saria/appimage.json` and
  are not moved.
- Releases carry three more files for Linux: `NX2Saria-update-linux.json`, `NX2Saria-app-linux-x86_64-<version>.zip`
  and `NX2Saria-runtime-linux-x86_64-<id>.zip`, checked against `SHA256SUMS.txt` like the Windows ones. Windows
  launchers read only their own manifest.
- An update downloads and checks the app (and the runtime when its id changes), switches the folders once the game has
  closed, and starts the new launcher in place (`os.execv`). A new version that cannot start (exit 86) is rolled back
  to the previous one, which is then not offered again.
- `launcher.log` starts with the system, the kind of install, the folder and the version, and has one line per install
  or update step, with times.

## Thread timing fixes (#47)

A ThreadSanitizer build of the host runtime for the bench (opt-in, never shipped; `docs/thread-sanitizer.md`) found
data races, now fixed:
- the virtual cores' wait hint and hand-over (`kernel.c`), the guest's start time, the priority and headroom state;
- the uniform snapshots' generation and drop queries (acquire and release);
- the mesh pipeline result, which now travels with its draw instead of through a shared variable;
- the replay counters, now counted per chunk and published in batches.

Nothing the player sees changes when these races did not hit. Bench, Kokiri Forest, four interleaved pairs: the CPU's
replay time per frame unchanged (8.77 ms), GPU busy within the noise.

## Smaller changes

- Apply in the settings menu leaves out of its list, and out of its restart decision, a key that a quality preset
  hands back at the value it already had: `menu: draft   GAME_RES: stays '1080', no change` (#48).
- The performance window line can say `bound: serial` when the CPU and the GPU take turns rather than one of them
  being full, with the rule logged once (`perf: bound verdicts of the window lines: ...`); `tools/bench.py`'s
  "Win bound" column follows it (#46).

## Tested

- Linux bench: the launcher under Xvfb at 1920x1080 and 1280x800, the install, update and roll-back steps in unit
  tests; the TSan and normal builds in Kokiri Forest and Hyrule Field with the HUD shown.
- Tests: `release_files_test`, `platform_linux_test`, `preset_check`, `perf_bound_check`, `tsan_build_test`,
  `usnap_concurrency_check`, `docs_i18n check`.
- Windows builds of each change by GitHub Actions.
- Not tried yet: the AppImage install and a real update on a player's Linux PC, and the Steam Deck.
