# NX2Saria 0.15.0 in detail

The option names, log lines and measurements behind the [0.15.0 release notes](../releases/v0.15.0.md).
How to install or update is in [the install guide](../install.md).

0.15.0 makes play smoother while pipelines are still being built, keeps the pipeline cache files from filling with
pipelines nothing uses any more, and survives presentation and sampler failures that used to end the game or misdraw
it. Each change writes to the game's log, so a report shows whether it is on and what it did.

## New

- **Background pipeline builds rest while play is heavy** (`bg_build_play_draws`, default 600).
  - The builds that run beside the game rest while the frame in play has 600 draws or more. Those are the background
    queue, the optimised builds that replace quick ones, and the driver cache warm-up.
  - They build in the light moments instead: the title, menus, the pause and map screens, and area loads.
  - A pipeline that a draw waits for is always built at once.
  - It helps while pipelines are still being built beside play, after an update or a driver change. In the Kokiri
    Forest at 1280x720 with the driver's cache empty, the average went from about 25 to 27-28 fps, and the slowest 1%
    of frames went from 64-70 ms to 59 ms. Once the caches are warm, it makes no difference.
  - `bg_build_play_draws = 0` builds in every frame, as before.
- **The pipeline cache follows the shader translator** (`pipeline_cache_stamp`, default on).
  - `pipeline-cache.id` names the translator whose pipelines `pipeline-cache.bin` and `pipeline-cache-play.bin` hold.
  - When a new translator no longer carries the old one's shaders over, both files are deleted once and filled again.
    Before, they kept the old pipelines for good: 650 MB with 15 to 18% of it used.
  - While the old shaders are still carried over, the files are read and kept.
  - A run that starts without `pipeline-cache.bin` writes it once when the game is closed. The next start reads those
    pipelines from it again.
- **Presentation and sampler failures no longer end the game:**
  - The swapchain's image list and semaphores are checked. A failed or incomplete one is made again at the next
    frame instead of being used half made.
  - The picture area the game asks for is cut to the image without overflowing, whatever the values.
  - Frame generation (DLSS and FSR 3.1) turns off cleanly when its presenter cannot make what it needs.
  - A sampler the driver refuses is tried again with simpler settings. If it still fails, the draw uses the default
    sampler and the sampler is tried again 250 ms later.
- **Their log** (`logs/nx2saria.log`):
  - At the start, one line for each says whether it is on and with what value, for example
    `vk: pipeline cache stamp 24f7e6cc matches: read, 27.3 MB`.
  - When the game closes, `vk: background builds paused in play: N frames, M builds deferred` gives the gate's counts.
  - Each failure is written as `gfx: <call> failed (<result>), N times: ...`, a limited number of times per run.

## For testers

- **Start straight in an area** (`boot_map = <area>[:<start position>]`, #5). The game loads the save of a slot and
  starts in that area, without the title screen or the file menu. The save file on disk does not change.
  - `boot_map_slot` picks the slot (0-5, or `latest`), `boot_map_age` the age (`child`, `adult` or `save`) and
    `boot_map_time` the time of day (`HH:MM` or `save`).
  - The log says where Link arrived: `boot map: arrived in ...`. A name that is not an area gives one line and the
    normal title.
  - `tools/run_game.py --boot-map` and `tools/bench.py --boot-map` start their runs this way.
  - `docs/boot-to-map.md` explains how it works.
- `docs/performance.md` says how to measure the play gate.

## Known issues

- **Tested on Linux only** (RX 6700, RADV), including a 39-minute session with the swapchain made again up to
  3440x1440. The Windows build was built and checked by the release workflow. 0.15.0 came out as a pre-release and
  became the stable release on 2026-11-17.
- **A run that is ended by force** rather than closed leaves `pipeline-cache.bin` unwritten after a deletion. The next
  run writes it instead.
- **Frame generation on Linux is 2x and SDR only**, as in 0.14.0.
- **AMD FSR 3.1 and FSR 4 can show visual glitches on Windows**, as in 0.14.0: black or dark patches and flicker while
  the camera or Link moves when the scene is rendered smaller than the picture, and trails behind moving characters.
  Bilinear upscaling, or the scene at the window's size with no upscaler, avoids the patches. Reported to the original
  project as tangerineturtle1/NX2navi#794, tangerineturtle1/NX2navi#475 and tangerineturtle1/NX2navi#736.
- **AMD FSR 3.1 frame generation on Windows adds few frames**, as in 0.14.0: most of the game's frames lack the depth
  and motion it needs there, so only a small share of them get a generated frame.
- **FSR 4 on Radeon RX 6000 (RDNA 2)**: AMD's driver offers FSR 4 on these cards and it runs, but it costs far more GPU
  time than on newer cards (about 12 ms a frame at 1440p on an RX 6750 XT). FSR 3.1 is the lighter choice there.
