# NX2Saria 0.27.0-rc.1 in detail

The log lines and tests behind the [0.27.0-rc.1 release notes](../releases/v0.27.0-rc.1.md). How to install or update
is in [the install guide](../install.md). It is the first release candidate of 0.27.0, for launchers on the Preview
channel, made from `main` after [0.26.0](v0.26.0.md).

## Fixes in the upscaler paths (#126)

Found by reading the notes of `docs/code/vk-upscalers.md` against the code and against the SDKs. None of these paths
runs on the project's test computer (an AMD card on Linux).

- **NGX calls go through one lock.** NVIDIA's NGX library is not thread safe. DLSS ran from the replay thread, its
  idle releases from the frame's bookkeeping, and on Linux the DLSS frame generation through NGX from the present
  thread, without a lock between them. Now every call takes one lock. Start: `dlaa: NGX calls go through one lock (NGX
  is not thread safe): ...`. In play, beside the DLSS line (evaluations 1, 300 and every 3600): `dlaa: NGX lock: N
  calls (replay ..., present ..., frame bookkeeping ..., setup ...), W waited ...: the present thread X times (longest
  ... ms), the others Y (longest ... ms); longest hold ... ms (...)`. On Windows the frame generation through NGX
  does not exist, so the lock is almost never waited for; one call without a wait costs about 41 ns.
- **FSR 4 frame generation resets after a frame that was not prepared.** The FSR 3.1 path already did; the FSR SDK
  2.4 path only counted the cut. The periodic `fg4` line gains `N preparations reset after a frame not prepared`.
- **The second sharpening pass is destroyed at the game's end on Linux**, and the loops over DLSS's sizes use the
  constant.
- **HDR: the tonemap splice makes two more comparisons** before it takes a shader's clamp. A shader it refuses is
  said once: `hdr: ... clamp(s) of a fitted ACES curve not taken ...` (the first 4 shaders).
- Test: `tests/ngx_lock_check.py` compiles `vk_dlaa.c` over a made-up NGX that reports overlapping calls: 164 of 315
  calls overlapped without the lock, 0 with it. On the test computer, with HDR armed, the game's real tonemap was
  spliced and no shader was refused; FSR 3.1 gave the same lines as before.
- Not shown on hardware: the overlap of NGX calls (Linux with a GeForce RTX 40 or 50), the FSR 4 reset (Windows with a
  Radeon) and the destroyed pass under the Vulkan validation layer, which ran out of memory before the game's end.
- Left as it is: the fixed camera planes of the FSR 4 frame generation, which need a session on Windows with a Radeon
  to decide. Notes: [code/vk-upscalers.md](../code/vk-upscalers.md).

## A crash summary carries the hardware and settings (#120)

A hard crash writes no session summary, so the launcher makes one from the `FATAL` line. Until now it had 36 of its 42
fields empty.

- The game writes `logs/session-start.json` three times while it starts (before any graphics device, after the
  device, and before the game begins) and once after each *Apply* in the settings menu: `telemetry: session header
  written to logs/session-start.json at <moment> (<n> bytes; gpu known|not yet known; startup known|not yet known)`.
- After a crash the launcher takes the system, processor, memory, graphics card, display, settings, start-up times,
  patches and mods from it: `telemetry: the last run ended in a crash; a summary was made from its FATAL line, with the
  hardware and settings of logs/session-start.json (N of 42 fields null)`, or `..., without hardware or settings:
  <why> (N of 42 fields null)`.
- The file holds only fields of a normal session report and is never sent itself. A crash inside the creation of the
  graphics device carries the system and the settings, not the card. What a report holds: [telemetry.md](../telemetry.md).
- On the test computer, with forced crashes: 7 of 42 fields empty after the game's start (the session's times and frame
  rates), 16 of 42 with no graphics device. Not shown: a real crash on Windows.

## The lines of a crash report are written whole (#127)

- The `FATAL` line, the host frames and the register lines were each written in several pieces, and a line of
  another thread could land between two of them. Each is now built in one buffer and written once; a line longer
  than the buffer ends with ` [line cut]`.
- With the log on a terminal instead of a file, the crash handler waited for a lock the crashed thread could hold. It
  now tries for 100 ms and writes without it, and says so in the log.
- The launcher, for logs of older versions: a `FATAL` line with a second log prefix inside is cut there, and its tail
  is put back only when the next piece has the shape of a `FATAL` line's end.
- Tests: `tests/fatal_line_check.py` crashes the game twenty times with four threads logging. Before: the line broken
  in 19 of 20 runs of each kind, and the terminal case never ended. After: whole in 20 of 20, and it ends.
  `tests/log_line_check.py`, `tests/log_cap_check.py` and the launcher's tests cover the rest.

## The source has no comments left

The comments of `runtime/vk` and of the launcher moved to `docs/code/` (#116, #118, #119, #121 to #124), and the two
checks now fail instead of warning (#125): a comment in the source, or a page that cites something that is not
there. No change of behaviour: the same tokens, objects and syntax trees before and after. The launcher's window was
not opened with these changes before this candidate.
