# NX2Saria 0.18.6 in detail

The option names, log lines and measurements behind the [0.18.6 release notes](../releases/v0.18.6.md).
How to install or update is in [the install guide](../install.md). How frame generation is counted and checked is in
[docs/frame-generation.md](../frame-generation.md).

0.18.6 is a pre-release to test frame generation on Windows (#20).

## Fixed

- **A frame shape that stuck for the whole session.** Before the first scene is set up, the game draws a
  half-resolution effect into three targets with a half-size depth. That pass was taken for a deferred G-buffer, and
  the "deferred" frame shape then stayed on until the game closed. With the scene smaller than the picture, frame
  generation lost its HUD-less picture (Windows refused those frames) and FSR 3.1 upscaling never found its output
  pass. Now a "G-buffer" smaller than a scene already set up is refused, and a light target larger than it undoes the
  shape. On the Linux bench, FSR 3.1 Quality with frame generation, 90 s: 1,049 gameplay frames and 0 generated with the
  old rule, 1,055 and 1,017 generated (96.4 %) with the new one.
- **The menu counted as missing inputs.** Frame generation now checks for an open menu before it takes the frame's
  depth and motion, and does not use them up while the menu is open.

## Changed

- **Frame generation's counts** (`fg:` lines) are kept by the game's state: gameplay, menu, and no scene (the title,
  movies, loading). Every 600 gameplay frames a line gives the frames generated, the presents and the frames a second
  on screen (the overlay's number), with the session's totals; 60 such lines, then one period in ten. The old lines
  counted the title and the movies with play, which is where the "few generated frames" of the Windows known issue
  came from: in play, the logs of Windows players show nearly every frame generated.
- **A `fg: path:` line at start** names the path (AMD's FSR 3.1 library, its 2.4 SDK, or the runtime's own passes) and
  the mode. On Windows the GPU time of each generated frame is measured (`fg: GPU time ...`).
- **Why frame generation does not run** (`dlaa: frame generation does not run: ...`): the setting is off; DLSS Frame
  Generation is chosen and this GPU has none (from Streamline's own support check: RTX 40 or newer), with
  `framegen = fsr3` suggested where AMD's FSR 3.1 frame generation runs; Streamline gives another reason (named); or it
  has not started yet.

## Tested

- Linux bench (RX 6700, RADV), Hyrule Field, 2560x1080, 120 s: FSR 3.1 Quality with frame generation 1,658 gameplay
  frames and 1,620 generated (97.7 %); frame generation alone 1,653 and 1,615 (97.7 %). GPU time 0.96 to 1.14 ms per
  generated frame.
- `tests/fg_stats_check.py` and `tests/fg_reset_check.py`; the Windows release workflow builds the runtime and the
  DLSS Frame Generation DLL with its exports. An independent review checked the Windows GPU timing (host query reset,
  timestamp support, no waits, nothing kept across swapchain changes), the frame shape rule and the counters.
- Not yet: the owner's Windows notebook (RTX 3050 Laptop) with FSR 3.1 frame generation, which is what this
  pre-release is for. The known issue about FSR 3.1 frame generation on Windows stays until that test confirms it.
